CSS Transitions

CSS transitions let you smoothly interpolate property values over time when they change, rather than having them snap instantly from one state to another. Before transitions existed, any style change — a hover effect, a class toggle from JavaScript, a focus state — would jump from the old value to the new one in a single frame. Transitions give you fine-grained control over that change, producing polished, professional-feeling interfaces with almost zero effort.

A transition is defined by four sub-properties: transition-property specifies which CSS property (or properties) to animate; transition-duration sets how long the animation takes; transition-timing-function controls the acceleration curve; and transition-delay adds an optional wait before the transition starts. You can combine all four into the transition shorthand, and you can comma-separate multiple transitions to animate different properties with independent durations and easing curves.

Not every CSS property can be transitioned. Only properties with interpolable values qualify — colors, lengths, percentages, transforms, opacity, and similar numeric or color-based values. Properties like display, font-family, or content historically could not be transitioned because there is no meaningful "midpoint" between their values (though modern CSS is changing this for display, as we will cover later). A good rule of thumb: if the browser can compute intermediate values between the start and end state, it is animatable.

One critical detail about transitions: they only fire when a property changes. They do not run on page load, and they do not run when an element first appears in the DOM. The element must already be rendered with one value, and then that value must change (via :hover, :focus, class change, etc.) for the transition to activate. This limitation is exactly what @starting-style was designed to solve, which we will cover in Section 5.

Why it matters: Transitions are the simplest way to add motion to your UI. They require no keyframes, no animation names, and no complex setup — just declare what to animate and for how long. Use them for hover states, focus rings, color shifts, and any interactive feedback. They are the bread and butter of polished web interfaces.

Transition Shorthand

/* Individual sub-properties */
.btn {
  transition-property: background-color, transform, box-shadow;
  transition-duration: 0.3s;
  transition-timing-function: ease;
  transition-delay: 0s;
}

/* Shorthand: property duration timing-function delay */
.btn {
  transition: background-color 0.3s ease,
              transform 0.2s ease-out,
              box-shadow 0.3s ease;
}

/* Transition ALL animatable properties (use with care) */
.btn {
  transition: all 0.3s ease;
}

Timing Functions

The timing function (also called the easing function) determines how a transition or animation progresses over its duration. A linear timing function moves at constant speed; an ease-in starts slowly and accelerates; an ease-out starts quickly and decelerates. The default ease keyword starts slow, speeds up in the middle, and slows again at the end — a pattern that mimics natural, physical motion and usually looks the most pleasing for UI interactions.

Under the hood, CSS timing functions are cubic Bézier curves defined by two control points. The keywords ease, linear, ease-in, ease-out, and ease-in-out are just aliases for specific cubic-bezier() values. For example, ease is cubic-bezier(0.25, 0.1, 0.25, 1.0). You can create your own curves with cubic-bezier(x1, y1, x2, y2) to get exactly the feel you want — snappy, bouncy, dramatic, or subtle. Tools like cubic-bezier.com let you visually design curves and preview them in real time.

CSS now also supports the linear() function (distinct from the linear keyword). This lets you define a custom easing curve by specifying a series of output values at evenly-spaced points or at explicit percentage stops. It is perfect for creating spring-like or bounce effects that cubic-bezier curves cannot express, since cubic-bezier is limited to a single curve segment while linear() can approximate any arbitrary curve through piecewise linear interpolation.

Choosing the right timing function is an essential part of your design language. Subtle ease-out transitions feel responsive and natural for UI interactions like hovering and clicking. Ease-in works well for elements leaving the screen because it accelerates away. Linear is appropriate for continuous, mechanical animations like progress bars or spinning icons. The difference between a polished interface and an amateur one often comes down to nothing more than the timing function.

Why it matters: Two animations with the same duration but different timing functions feel completely different. The easing curve communicates personality, weight, and intentionality. Master timing functions and your UI will feel alive rather than mechanical. This is the closest CSS gets to giving objects a sense of physical weight.

Timing Function Options

/* Named keywords */

@keyframes Animations

While transitions animate between two states when a property changes, @keyframes animations let you define multi-step sequences that can run automatically, loop infinitely, reverse direction, and control every stage of the motion independently. You declare a named set of keyframes with @keyframes animation-name { ... }, then apply it to an element with the animation property. This two-step approach separates the definition of the motion from its application, making animations reusable across multiple elements.

Inside a @keyframes block, you specify style rules at specific points using percentages (0%, 25%, 50%, 100%) or the aliases from (equivalent to 0%) and to (equivalent to 100%). The browser interpolates between these keyframes automatically. You can define as many percentage stops as you need, which is what makes keyframes so powerful — you can create complex, multi-phase animations with different properties changing at different times, something transitions simply cannot express.

The animation shorthand accepts up to eight sub-properties: animation-name, animation-duration, animation-timing-function, animation-delay, animation-iteration-count (a number or infinite), animation-direction (normal, reverse, alternate, alternate-reverse), animation-fill-mode (none, forwards, backwards, both), and animation-play-state (running, paused). The fill mode is especially important: forwards keeps the element in its final keyframe state after the animation ends, while backwards applies the first keyframe's styles during any delay period before the animation starts.

Performance matters significantly with animations. Properties like transform and opacity are composited by the GPU and animate very efficiently without triggering layout or paint. Animating width, height, top, left, or margin triggers layout recalculations every frame and can cause visible jank on lower-powered devices. Always prefer transform: translateX() over left, and transform: scale() over width/height changes when possible.

Why it matters: Keyframe animations power loading spinners, attention-grabbing pulses, entrance effects, and complex choreographed motion sequences. Combined with custom properties and timing functions, they let you build rich, engaging experiences that were once only possible with JavaScript animation libraries like GSAP or Framer Motion.

@keyframes Syntax

@keyframes spin {
  from { transform: rotate(0deg); }
  to   { transform: rotate(360deg); }
}

@keyframes bounce {
  0%, 100% {
    transform: translateY(0) scaleX(1.1) scaleY(0.9);
  }
  50% {
    transform: translateY(-50px) scaleX(1) scaleY(1);
  }
}

/* Apply with shorthand */
.spinner { animation: spin 1s linear infinite; }
.ball    { animation: bounce 0.6s ease-in-out infinite; }

/* Multiple animations on one element */
.complex {
  animation:
    fadeIn 0.5s ease forwards,
    slideUp 0.5s ease forwards;
}

Transform Functions

The transform property applies geometric transformations to elements without affecting document flow. Unlike changing top/left or margin, transforms do not trigger layout recalculation — the element's original space in the document is preserved, and the visual rendering is modified on the compositor layer. This makes transforms ideal for animations and transitions because they are GPU-accelerated and extremely performant even on mobile devices.

The core 2D transform functions are translate(x, y) for moving an element, rotate(angle) for spinning it, scale(x, y) for resizing it, and skew(x, y) for shearing it. You can chain multiple functions in a single transform declaration — they compose right to left (like matrix multiplication), so the order matters. The transform-origin property controls the point around which transforms are applied; it defaults to the center of the element but can be set to any edge, corner, or arbitrary coordinate.

CSS also supports 3D transforms through perspective(), rotateX(), rotateY(), rotateZ(), translateZ(), and scale3d(). To enable 3D rendering, you need to set perspective on a parent element (which defines how far the viewer is from the Z=0 plane) and optionally transform-style: preserve-3d on the transformed element so that child elements participate in the same 3D space rather than being flattened. The backface-visibility property controls whether the back face of a rotated element is visible — essential for card-flip effects.

Modern CSS has also introduced individual transform properties: translate, rotate, and scale as standalone properties separate from the transform shorthand. These can be transitioned independently without overriding each other, solving the long-standing problem where setting transform in a hover state would override a transform set in the base state. This is a significant quality-of-life improvement for complex interactive elements that need multiple transforms applied at different times.

Why it matters: Transforms are the backbone of performant CSS animation. They run on the GPU, do not trigger layout recalculations, and can express complex spatial changes. The 3D subset unlocks card flips, page turns, parallax effects, and immersive visual experiences — all in pure CSS without a single line of JavaScript.

Transform Examples

/* 2D transforms */
.moved   { transform: translate(50px, 20px); }
.rotated { transform: rotate(45deg); }
.scaled  { transform: scale(1.5); }
.skewed  { transform: skewX(-10deg); }

/* Chained transforms (right-to-left order) */
.combo {
  transform: translate(100px, 0) rotate(45deg) scale(0.8);
}

/* 3D card flip setup */
.card-container { perspective: 1000px; }
.card {
  transform-style: preserve-3d;
  transition: transform 0.6s ease;
}
.card:hover { transform: rotateY(180deg); }
.card-front, .card-back {
  backface-visibility: hidden;
}
.card-back { transform: rotateY(180deg); }

@starting-style

One of the longest-standing frustrations with CSS transitions was the inability to animate an element's initial appearance. When an element first renders — whether it is in the HTML on page load, inserted via JavaScript, or switching from display: none to display: block — there is no "previous state" for the browser to transition from. The element just appears instantly. Developers resorted to JavaScript-based workarounds, requestAnimationFrame hacks, or keyframe animations to fake entry transitions.

@starting-style solves this problem elegantly. It lets you declare what an element's styles should be at the moment it first becomes visible (its "before-change" style). The browser then immediately transitions from those starting styles to the element's actual computed styles. This means you can now use regular CSS transitions for entrance animations — no keyframes needed, no JavaScript timing hacks needed. The animation is driven by the same transition engine, giving you all the control of timing functions and delays.

The syntax is straightforward: you nest a @starting-style block inside a rule (or write it as a standalone block referencing the selector). Inside, you set the initial values for any properties you want to transition. The element must also have a transition declared on those properties in its normal styles. When the element first renders, the browser applies the starting styles as its "before" state, then transitions to the normal styles as the "after" state.

@starting-style works hand-in-hand with transition-behavior: allow-discrete and the overlay property to enable full enter/exit animations for elements toggling display: none, popovers, and dialogs. Together, these features finally bring CSS to parity with what JavaScript animation libraries have offered for years — but with zero JavaScript, full browser optimization, and native accessibility support. You can stagger entrance animations by combining @starting-style with transition-delay and custom properties.

Why it matters: Entry animations are everywhere in modern UI — modals fading in, cards sliding up, notifications appearing, page sections revealing on scroll. @starting-style makes these trivial in pure CSS, without the complexity of keyframe animations or the overhead of JavaScript animation libraries. It is one of the most impactful recent additions to CSS.

@starting-style Syntax

/* Cards that fade and slide in on first render */
.card {
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.5s ease,
              transform 0.5s ease;

  /* Nested @starting-style */
  @starting-style {
    opacity: 0;
    transform: translateY(30px);
  }
}

/* Staggered delays with custom properties */
.card {
  transition-delay: calc(var(--i, 0) * 0.15s);
}

/* Also works as a standalone at-rule */
@starting-style {
  .card {
    opacity: 0;
    transform: translateY(30px);
  }
}

interpolate-size

Animating to or from height: auto has been one of the most requested features in CSS for well over a decade. The classic problem: you have a collapsible section whose expanded height depends on its content. You want it to smoothly open and close. But CSS transitions cannot interpolate between a fixed value (like 0) and the keyword auto — they need two numeric endpoints. Developers have resorted to max-height hacks (which produce bad timing and wasted animation frames), JavaScript measurement with getBoundingClientRect(), or the Web Animations API.

The interpolate-size property changes this entirely. When set to allow-keywords, it tells the browser that it is acceptable to interpolate sizing keywords like auto, min-content, max-content, and fit-content as if they were numeric values. The browser resolves the keyword to its computed pixel value at each animation frame and interpolates smoothly. You can set this on :root to enable it globally across your entire page, or scope it to specific components.

This unlocks the smooth accordion pattern without any JavaScript. A <details>/<summary> element naturally toggles its content visibility when clicked. By transitioning the height of the content area and enabling interpolate-size: allow-keywords, you get a native, accessible, keyboard-navigable, smooth-opening disclosure widget. The same technique works for any expandable UI component — dropdown menus, expandable cards, collapsible sidebars, and FAQ sections.

There is also the calc-size() function, which lets you perform calculations with intrinsic sizing keywords in contexts where they previously were not allowed. For example, calc-size(auto, size * 0.5) would resolve to half of the auto height. While interpolate-size is the simpler approach for most animation needs and requires only a single property declaration, calc-size() gives you fine-grained mathematical control for more advanced sizing scenarios.

Why it matters: Smooth height animations are ubiquitous in UI design — accordions, expandable rows, dropdown menus, collapsible panels. interpolate-size eliminates the need for JavaScript-based height measurement and the infamous max-height hack, giving us a clean, performant, pure-CSS solution that works with native HTML elements like <details>.

Smooth Accordion CSS

/* Enable keyword interpolation */
:root {
  interpolate-size: allow-keywords;
}

/* The accordion body transitions height */
.accordion-body {
  height: 0;
  overflow: hidden;
  transition: height 0.4s ease;
}

/* When the details element is open, height becomes auto.
   With interpolate-size, the browser smoothly animates
   from 0 to the resolved auto value. */
details[open] .accordion-body {
  height: auto;
}

What is interpolate-size? +

The interpolate-size property allows CSS to smoothly transition between fixed values and keyword sizes like auto. By setting interpolate-size: allow-keywords, the browser will resolve keyword values to their computed pixel equivalents at each animation frame, enabling smooth height transitions that were previously impossible without JavaScript.

How does it differ from the max-height hack? +

The max-height hack requires you to set an arbitrary large value (like max-height: 1000px) and transition that. This creates timing issues — if the actual height is 200px but you transition from 0 to 1000px, the visual animation finishes in the first 20% of the duration and the rest is wasted time. Additionally, the closing animation feels wrong because it starts with an invisible delay. interpolate-size transitions to the exact computed height, so timing is always perfect in both directions.

What about browser support? +

As of 2025, interpolate-size is supported in Chrome/Edge 129+ and Safari 17.5+. Firefox support is in development. For older browsers, the accordion will still function perfectly — clicking the summary will still reveal the content — it just will not animate smoothly. This makes it an ideal progressive enhancement: the feature works everywhere, and the smooth animation is a bonus in supporting browsers.

Can I use it with grid or flexbox? +

Yes! interpolate-size works with any sizing context. You can use it to smoothly transition flex-basis, grid track sizes, or any dimension property that involves keyword values. It pairs especially well with CSS Grid's auto track sizing for smooth row expansion and collapse effects without JavaScript calculation.

Display None Animations

Historically, you could never transition to or from display: none. The display property is discrete — there is no halfway point between "rendered" and "not rendered." When you set display: none, the browser would snap the element out of existence immediately, cutting off any opacity fade or transform slide you tried to apply. Developers worked around this with visibility: hidden combined with opacity: 0, or by using JavaScript to delay the display: none until after an animation completed via transitionend event listeners.

The new transition-behavior: allow-discrete property (or the allow-discrete value used inline in the transition shorthand) changes the game. When applied, the browser changes how discrete properties like display participate in transitions. Instead of snapping immediately, the browser keeps the element rendered throughout the full transition duration and only applies the discrete change (to display: none) at the very end. For entry transitions (going to display: block), the discrete change happens at the very start, giving the rest of the transition time to fade in.

This works especially well with the <dialog> element and the Popover API. The dialog element has a ::backdrop pseudo-element that can also be transitioned. Combined with @starting-style for the entry animation, you can create a modal that smoothly fades in when .showModal() is called and smoothly fades out when closed — toggling display: none under the hood — with nothing but CSS declarations.

The overlay property is another piece of this puzzle for top-layer elements. Dialogs and popovers live in the browser's top layer, which is above everything else on the page. Without transitioning overlay, the element would leave the top layer immediately when closing, visually popping behind other content before its fade-out animation completes. Adding transition: overlay 0.3s allow-discrete keeps the element in the top layer for the duration of its exit transition. Together, transition-behavior, @starting-style, and overlay form a complete system for animating element visibility.

Why it matters: Almost every UI pattern involves showing and hiding elements — modals, tooltips, dropdowns, notifications, sidebar menus. Being able to smoothly animate display: none transitions in pure CSS eliminates an entire category of JavaScript animation code, the timing bugs that come with it, and the need for libraries like React Transition Group.

Animating Display with transition-behavior

/* A dialog with smooth enter and exit */
dialog[open] {
  opacity: 1;
  transform: scale(1);
  transition:
    opacity 0.3s ease,
    transform 0.3s ease,
    display 0.3s ease allow-discrete,
    overlay 0.3s ease allow-discrete;

  @starting-style {
    opacity: 0;
    transform: scale(0.9);
  }
}

/* Exit state */
dialog {
  opacity: 0;
  transform: scale(0.9);
}

Practical Patterns

The real power of CSS motion becomes clear when you combine transitions, animations, transforms, and modern features into practical UI patterns. Each pattern below demonstrates a real-world use case that you will encounter in production applications. These are not theoretical exercises — they are the exact techniques used by design systems at companies like Google (Material Design), Stripe, Linear, and Vercel to create interfaces that feel responsive, polished, and intentional.

Good motion design follows a few core principles: it should be purposeful (guiding attention or communicating state), quick (200-500ms for most interactions, shorter for small elements), and respectful of user preferences (via prefers-reduced-motion). Every animation should answer the question "what does this communicate to the user?" If the answer is "nothing" or "it just looks cool," remove it or simplify it. If it communicates a state change, a spatial relationship, or interactive feedback, refine it until it feels natural.

Performance is non-negotiable for production animations. Stick to the efficient properties — primarily transform and opacity, which are composited on the GPU without triggering layout or paint. Use will-change sparingly and only when you observe actual jank, as a hint for the browser to promote elements to their own compositor layer. And always test on low-powered devices; an animation that runs at 60fps on your development machine might be janky on a budget Android phone or an older iPad.

Accessibility is equally important and must not be an afterthought. Always wrap non-essential motion in a @media (prefers-reduced-motion: no-preference) query, or provide reduced alternatives in @media (prefers-reduced-motion: reduce). Some users experience motion sickness (vestibular disorders), seizure disorders, or simply find animations distracting. Respecting the prefers-reduced-motion setting is not optional — it is a core accessibility requirement under WCAG 2.3.3 and reflects a basic respect for your users.

Why it matters: Knowing syntax is only half the battle. The other half is knowing which patterns to apply, when to apply them, and how to implement them performantly. These practical examples give you a production-ready toolkit of motion patterns you can adapt to any project, from marketing sites to complex web applications.

Exercise: Animated Interactive Card

Create an animated card component that demonstrates three modern CSS motion techniques working together in a single, cohesive element:

  1. Entry animation with @starting-style: The card should fade in (opacity 0 to 1) and slide up (translateY(30px) to translateY(0)) when it first renders. Use @starting-style and CSS transitions — not keyframe animations. The transition should take 0.5 seconds with an ease timing function.
  2. Hover lift effect: On hover, the card should smoothly lift up by 8px (translateY(-8px)) and gain a larger, softer box-shadow to simulate elevation. The transition should use ease-out timing and last approximately 250ms for a responsive, natural feel.
  3. Pulsing notification badge: Add a small circular badge (roughly 18px) in the card's top-right corner that pulses continuously using a @keyframes animation. It should scale between 1 and 1.2 and have a glowing box-shadow that expands and fades in sync with the scale.

Bonus: Add a @media (prefers-reduced-motion: reduce) block that disables the pulse animation entirely and replaces the entry slide with a simple opacity fade (remove the translateY but keep the opacity transition). This ensures your component is accessible to users with vestibular sensitivities.

Challenge: Animated Onboarding Flow

Build a multi-step onboarding wizard that showcases the full range of CSS motion techniques covered in this module. This is a complex project that ties together everything you have learned:

  1. Staggered entrance: When each step appears, its content elements (icon, heading, description, form fields) should animate in with staggered delays using @starting-style or keyframe animations. Each element should enter 100-150ms after the previous one.
  2. Smooth height transitions: The wizard container should smoothly resize when switching between steps of different content heights, using interpolate-size: allow-keywords to transition the container's height to auto.
  3. Step indicators: A progress bar or step dots at the top should animate smoothly between states, using transitions for color changes and transforms for the active indicator. Consider a sliding underline or an expanding progress fill.
  4. Loading state: After the final step's "submit" action, show a loading state with a skeleton shimmer pattern, then transition to a success state with a checkmark that draws itself using stroke-dashoffset animation on an SVG path.
  5. Exit animations: When leaving a step, content should fade out and slide in the direction of navigation (left for "next," right for "back") before the new step enters from the opposite direction. This creates a natural lateral flow.

Use the radio button hack for step navigation — no JavaScript allowed. Each step is controlled by a radio input, and CSS :checked selectors drive all the visibility and animation states. Apply prefers-reduced-motion to provide a reduced-motion alternative that uses simple crossfades instead of sliding transitions. The entire flow should be built with semantic HTML and work without CSS (content should still be readable as a plain document).
