1. Media Queries

Media queries are the foundation of responsive design. They let you apply CSS rules conditionally, based on characteristics of the device or viewport. The @media rule wraps a block of CSS that only takes effect when the specified condition is true.

The most common condition is viewport width. You test it with min-width (styles apply when the viewport is at least this wide) or max-width (styles apply when the viewport is at most this wide). You can combine conditions with and, use or (comma-separated), and negate with not.

The choice between min-width and max-width determines your design strategy. min-width queries add styles as the viewport grows — this is the mobile-first approach. max-width queries override styles as the viewport shrinks — the desktop-first approach. Modern best practice strongly favors mobile-first with min-width.

Why this matters: Media queries are how you speak to different devices. Without them, your layout is a one-size-fits-all solution that inevitably fails on some screen size. They are the conditional logic of visual design — as fundamental as if statements in programming. 
/* Mobile-first: base styles for small screens */
.box { background: coral; padding: 1rem; }

/* Tablet and up */
@media (min-width: 768px) {
  .box { background: dodgerblue; }
}

/* Desktop and up */
@media (min-width: 1024px) {
  .box { background: mediumseagreen; }
}

/* Combining conditions */
@media (min-width: 768px) and (max-width: 1023px) {
  .box { border: 3px solid gold; }
}

/* Orientation, hover capability, color-scheme */
@media (orientation: landscape) { /* ... */ }
@media (hover: hover) { /* device has hover */ }
@media (prefers-color-scheme: dark) { /* ... */ }

2. Mobile-First

Mobile-first means writing your base CSS for the smallest screens, then progressively adding complexity for larger viewports using min-width media queries. This is not just a technical pattern — it is a design philosophy. Start with the essential content and functionality, then enhance.

The practical reason is performance. Mobile devices are slower and have less bandwidth. If you start with desktop styles and override them for mobile, the mobile browser downloads and parses CSS it will never use. With mobile-first, the smallest devices get the simplest CSS. Larger devices, which are more powerful, handle the additional rules with ease.

There is also a design clarity argument. Designing for a small screen forces you to prioritize. You cannot fit everything on a 320px screen, so you have to decide what truly matters. This constraint leads to cleaner, more focused interfaces at every breakpoint.

Why this matters: Mobile traffic accounts for over 60% of web visits worldwide. Building mobile-first ensures the majority of your users get an optimized experience. It is also easier to add than to take away — progressive enhancement is more maintainable than progressive degradation. 
/* Base: single column, simple layout */
.container {
  display: flex;
  flex-direction: column;
  gap: 1rem;
  padding: 1rem;
}

.sidebar { order: 2; }
.content { order: 1; }

/* Tablet: side-by-side */
@media (min-width: 768px) {
  .container {
    flex-direction: row;
  }
  .sidebar {
    order: 0;
    flex: 0 0 250px;
  }
  .content {
    flex: 1;
  }
}

/* Desktop: wider sidebar, more padding */
@media (min-width: 1024px) {
  .container {
    gap: 2rem;
    padding: 2rem;
  }
  .sidebar {
    flex: 0 0 300px;
  }
}

3. Common Breakpoints

While there is no universally "correct" set of breakpoints, the industry has converged on a handful of commonly used values that align with device categories. These are not magic numbers — they are practical defaults based on real-world device data.

480px — Large phones in portrait. Use this when your mobile layout needs a minor adjustment for slightly wider phones. Not always necessary, but useful for typography bumps or switching from single to two-column grids on small items.

768px — Tablets in portrait, small laptops. This is often the first major layout shift. Sidebars appear, navigation expands, and multi-column layouts begin. It is the most universally used breakpoint.

1024px — Tablets in landscape, standard laptops. Full desktop layouts typically activate here. Navigation becomes horizontal, content widths increase, and you can safely show more information side-by-side.

1280px — Large desktops and wide monitors. Use this for max-width containers, extra whitespace, or showing additional columns of content. Beyond this, you are typically just centering content with more margin.

Why this matters: Do not add breakpoints arbitrarily. Add a breakpoint when your design breaks — when content becomes unreadable, layouts look awkward, or whitespace becomes excessive. Let the content dictate the breakpoints, and use these common values as sensible starting points. 
/* Common breakpoint system */
/* Base: 0 - 479px   (small phones) */
/* sm:   480px+      (large phones) */
/* md:   768px+      (tablets) */
/* lg:   1024px+     (laptops/desktops) */
/* xl:   1280px+     (large desktops) */

@media (min-width: 480px)  { /* sm */ }
@media (min-width: 768px)  { /* md */ }
@media (min-width: 1024px) { /* lg */ }
@media (min-width: 1280px) { /* xl */ }

4. Fluid Typography

Traditional responsive typography uses media queries to set different font sizes at different breakpoints. This creates abrupt jumps. Fluid typography uses the clamp() function to create text that scales smoothly and continuously between a minimum and maximum size.

The syntax is clamp(min, preferred, max). The browser uses the preferred value but never goes below min or above max. The preferred value typically uses viewport units (vw) so it scales with the browser width. For example, clamp(1rem, 2.5vw, 2rem) means: "be 2.5% of the viewport width, but never smaller than 1rem or larger than 2rem."

A practical formula for calculating fluid type: pick your minimum font size (e.g., 16px at 320px viewport) and maximum (e.g., 24px at 1200px viewport). The preferred value becomes a mix of a fixed value and a vw unit that interpolates between them. Tools like Utopia automate this calculation.

Why this matters: Fluid typography eliminates awkward jumps between breakpoints and reduces the number of media queries you need. It creates a more polished user experience and works seamlessly across every viewport width, not just the ones you explicitly designed for. 
/* Fluid typography with clamp() */
h1 {
  font-size: clamp(1.75rem, 1rem + 3vw, 3.5rem);
}

h2 {
  font-size: clamp(1.25rem, 0.75rem + 2vw, 2.25rem);
}

p {
  font-size: clamp(0.95rem, 0.85rem + 0.5vw, 1.15rem);
}

/* The three values mean: */
/* min:       smallest the text will ever be */
/* preferred: ideal size, scales with viewport */
/* max:       largest the text will ever be */

5. Viewport Units

Viewport units let you size elements relative to the browser window itself. 1vw equals 1% of the viewport width; 1vh equals 1% of the viewport height. These are powerful for creating full-screen sections, hero banners, and elements that scale with the window.

However, vh has a notorious problem on mobile browsers. When the address bar is visible, the viewport is shorter. When you scroll and the address bar hides, the viewport gets taller. Using 100vh for a full-screen hero causes layout jumps and content to be cut off behind the address bar on iOS and Android.

CSS introduced new viewport units to fix this: dvh (dynamic viewport height) changes as the address bar shows/hides, svh (small viewport height) uses the smallest possible viewport (address bar visible), and lvh (large viewport height) uses the largest possible viewport (address bar hidden). For most full-screen sections, dvh or svh is what you want.

Why this matters: The 100vh mobile bug has frustrated developers for years. Understanding the new viewport units and when to use each one prevents a class of layout bugs that are hard to debug on desktop but obvious on phones. Use svh for hero sections to guarantee content is never cut off. 
/* Classic viewport units */
.hero { height: 100vh; }              /* Buggy on mobile */
.half-screen { height: 50vw; }

/* New viewport units (use these!) */
.hero { height: 100dvh; }             /* Dynamic: follows address bar */
.hero { height: 100svh; }             /* Small: safest, always visible */
.hero { height: 100lvh; }             /* Large: assumes bar is hidden */

/* Mixing viewport units */
.sidebar { width: 25vw; min-width: 200px; max-width: 400px; }
.spacer  { margin-top: 5vh; }

6. Responsive Images

Images are one of the biggest challenges in responsive design. You need the right resolution for each device (so phones do not download desktop-sized images), the right aspect ratio for each layout, and proper scaling so images never overflow their containers.

The srcset attribute on <img> lets you provide multiple image files at different resolutions. The browser picks the most appropriate one based on viewport size and device pixel ratio. The sizes attribute tells the browser how wide the image will be rendered, which helps it make a smarter choice.

CSS properties object-fit and object-position control how an image fills its box. object-fit: cover scales the image to fill the box while maintaining aspect ratio (cropping the excess). object-fit: contain scales to fit entirely within the box (leaving gaps). The aspect-ratio property lets you set a box's proportions without padding hacks.

Why this matters: Images account for the majority of page weight on most websites. Serving appropriately sized images can cut load times by 50% or more on mobile. And using object-fit with aspect-ratio eliminates layout shift as images load — a core Web Vital (CLS). 
<!-- Responsive image with srcset -->
<img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w,
          photo-800.jpg 800w,
          photo-1200.jpg 1200w"
  sizes="(min-width: 1024px) 50vw, 100vw"
  alt="Responsive photo"
>

/* CSS for responsive image containers */
.image-card {
  aspect-ratio: 16 / 9;
  overflow: hidden;
  border-radius: 8px;
}

.image-card img {
  width: 100%;
  height: 100%;
  object-fit: cover;
  object-position: center;
}

7. Responsive Patterns

Certain layout patterns appear on nearly every responsive website. Mastering these patterns gives you a toolkit of proven solutions that you can adapt to any project. Below are three of the most essential: a responsive navigation, a card grid, and a collapsible sidebar.

Pattern 1: Responsive Navigation

On mobile, navigation links typically stack vertically or hide behind a hamburger menu. On desktop, they spread horizontally. The key is using flex-direction to switch between column and row layouts at a breakpoint. 

.nav {
  display: flex;
  flex-direction: column;   /* Mobile: stacked */
  gap: 0.5rem;
}

@media (min-width: 768px) {
  .nav {
    flex-direction: row;    /* Desktop: horizontal */
    align-items: center;
    gap: 2rem;
  }
}

Pattern 2: Responsive Card Grid

Cards should reflow based on available space. On mobile they stack, on tablet they form two columns, and on desktop three or more. CSS Grid with auto-fit and minmax() can handle this without any media queries. 

.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 1.5rem;
}

Pattern 3: Collapsible Sidebar

A sidebar that sits beside the content on desktop and collapses above or below it on mobile. This is the classic two-panel layout that adapts gracefully with a single flex-direction change. 

.layout {
  display: flex;
  flex-direction: column;
}

.layout-sidebar {
  padding: 1rem;
  background: var(--pe7-surface-2);
}

@media (min-width: 768px) {
  .layout {
    flex-direction: row;
  }
  .layout-sidebar {
    flex: 0 0 250px;
  }
  .layout-main {
    flex: 1;
  }
}

8. A Complete Responsive Page

Everything comes together in a full page layout. A real responsive page combines media queries, fluid typography, responsive images, and layout patterns into a cohesive whole that transforms seamlessly across breakpoints. The demo below is a miniature landing page that demonstrates all these techniques working together.

Notice how the layout shifts at each breakpoint: the hero section adjusts its padding and text size, the features grid reflows from one column to two to three, the navigation switches from stacked to horizontal, and spacing increases as more room becomes available. Every transition is smooth and intentional. 

/* The recipe for a responsive page */
/* 1. Mobile-first base styles */
/* 2. Fluid typography with clamp() */
/* 3. Flexible layout with flex/grid */
/* 4. Breakpoints where the design needs them */
/* 5. Responsive images with object-fit */
/* 6. Viewport units for full-screen sections */

.page { font-size: clamp(0.95rem, 0.85rem + 0.5vw, 1.1rem); }
.hero { min-height: 80svh; }
.features { grid-template-columns: repeat(auto-fit, minmax(250px, 1fr)); }
.nav { flex-direction: column; }
@media (min-width: 768px) { .nav { flex-direction: row; } }
