Component-Aware Design

Container queries and subgrid let components adapt to their context, not the viewport — unlocking truly reusable, layout-aware UI.

1. Why Container Queries

For over a decade, responsive design has been synonymous with media queries. We test the viewport width and rearrange layouts accordingly. This works well for page-level layout decisions — switching from a single column on phones to a multi-column layout on desktops — but it falls apart at the component level.

Consider a product card component. That card might appear in a narrow sidebar, a medium-width content area, or a full-bleed hero section. With media queries alone, the card has no idea where it lives. A @media (min-width: 768px) rule fires based on the browser window, not the card's container. The sidebar card and the main-area card both receive the same styles, even though one has 250px of space and the other has 800px.

This mismatch has driven developers to create brittle workarounds: special modifier classes (.card--sidebar, .card--main), JavaScript resize observers, or duplicated component variants. Every workaround adds complexity and fights against the goal of truly reusable components.

Component-Driven Design

Container queries flip the model: instead of asking "how wide is the viewport?", a component asks "how wide is my container?" This means a single card component can adapt its layout based on the space it actually has available. Drop it in a sidebar? It goes compact. Drop it in a wide content area? It goes horizontal. No modifier classes, no JavaScript, no duplication. The component is truly self-contained and context-aware.

This is the design philosophy behind every modern component framework — now CSS natively supports it.

Container Queries vs Media Queries: An Architectural Shift

Media queries are page-aware: they respond to the viewport, which is a global property shared by every component on the page. Container queries are component-aware: they respond to the size of the component's immediate container, which is local and independent. This distinction changes CSS architecture fundamentally. With media queries, a component's responsive behavior depends on where it is used — a card in a sidebar and a card in the main content area both react to the same viewport width, even though their available space is completely different. With container queries, components become truly portable, self-contained responsive units. You write the responsive rules once, and the component adapts correctly regardless of which layout context it lands in. In a design system, this eliminates entire categories of modifier classes, layout-specific overrides, and the JavaScript resize observers that were previously required to bridge the gap.

Container queries landed in all major browsers in 2023 and have been stable since. Combined with container query units, they give components fine-grained control over their presentation based on the dimensions of their nearest containment context.

2. Container Setup

Before you can query a container, you must explicitly designate an element as a containment context. This is done with the container-type property. Without it, @container rules have nothing to measure against.

The container-type property accepts three values:

  • inline-size — enables containment on the inline axis (width in horizontal writing modes). This is the most common choice because we almost always want to query width, and it preserves intrinsic block-size behavior.
  • size — enables containment on both inline and block axes. Use this when you also need to query height, but be aware it means the element's height can no longer depend on its content without explicit sizing.
  • normal — the default. No containment, no container queries.

You can also give a container a name with container-name, which lets nested components target a specific ancestor container rather than just the nearest one. The shorthand container combines both:

/* Longhand */
.sidebar {
  container-type: inline-size;
  container-name: sidebar;
}

/* Shorthand: name / type */
.sidebar {
  container: sidebar / inline-size;
}

/* Multiple names (rare but possible) */
.widget-area {
  container: widget panel / inline-size;
}

Once a container is established, any descendant can use @container rules to query its dimensions. The browser walks up the DOM tree to find the nearest ancestor with containment and measures against that element.

The Containment Cost of Container Queries

Setting container-type: inline-size is not free. It implicitly applies contain: layout style inline-size to the element. This containment means the element can no longer size itself based on its children's intrinsic inline size — it cannot "shrink-wrap" to fit its content width. The element's inline size must be determined by its own constraints (explicit width, grid/flex sizing, or the available space from its parent), never by measuring what is inside it. This is a deliberate trade-off: the browser needs this guarantee to avoid circular dependencies when evaluating container queries. In practice, this causes problems when you apply container-type: inline-size to elements that rely on intrinsic sizing — such as inline elements, absolutely positioned elements without explicit widths, or flex/grid items that use fit-content. A PE7 understands this constraint and chooses the containment context carefully, typically applying it to structural wrapper elements that already have an externally determined width rather than to content-driven elements.

3. @container Queries

The @container at-rule works similarly to @media but tests the dimensions of a containment context rather than the viewport. The syntax supports the same comparison operators (min-width, max-width, or the modern range syntax):

/* Classic syntax */
@container (min-width: 400px) {
  .card { flex-direction: row; }
}

/* Range syntax (preferred) */
@container (width >= 400px) {
  .card { flex-direction: row; }
}

/* Targeting a named container */
@container sidebar (width < 300px) {
  .card { font-size: 0.875rem; }
}

/* Combining conditions */
@container (width >= 300px) and (width < 600px) {
  .card { grid-template-columns: 1fr 2fr; }
}

Container queries also introduce a family of container query length units that resolve relative to the queried container's dimensions. These are invaluable for fluid sizing within components:

  • cqw — 1% of the container's width
  • cqh — 1% of the container's height (requires container-type: size)
  • cqi — 1% of the container's inline size
  • cqb — 1% of the container's block size
  • cqmin — the smaller of cqi and cqb
  • cqmax — the larger of cqi and cqb

These units let you create truly fluid component typography and spacing. A heading set to font-size: clamp(1rem, 4cqi, 2rem) scales with its container, not the viewport — perfect for reusable components.

/* Fluid component typography */
.card-title {
  font-size: clamp(1rem, 4cqi, 1.75rem);
}

/* Responsive padding based on container */
.card-body {
  padding: clamp(0.75rem, 3cqi, 2rem);
}

/* Container-relative gaps */
.card-grid {
  gap: clamp(0.5rem, 2cqi, 1.5rem);
}

One key difference from media queries: container queries cannot test the container element itself — only its descendants. This prevents circular dependencies where changing a container's layout would change its size, which would change the query result, which would change the layout again. The containment model ensures a clean, one-directional flow of information.

4. Style Queries

Container queries aren't limited to dimensions. Style queries let you query the computed value of custom properties on a container. This opens up a powerful pattern: parent components can set a custom property, and child components can adapt their rendering based on that property's value.

The syntax uses the style() function inside a @container rule:

/* Query a custom property value */
@container style(--theme: dark) {
  .card {
    background: #1a1a2e;
    color: #e0e0e0;
  }
}

@container style(--theme: light) {
  .card {
    background: #ffffff;
    color: #1a1a2e;
  }
}

/* Query for any truthy custom property */
@container style(--featured: true) {
  .card {
    border: 2px solid gold;
    transform: scale(1.02);
  }
}

Style queries are particularly powerful for building variant systems. Instead of adding modifier classes, you set a custom property on a container and let descendants respond. This keeps the component API clean and composable — you can combine multiple style flags without an explosion of class combinations.

Currently, style queries work with custom properties. The CSS Working Group is exploring support for querying standard properties in the future, but custom property queries alone are remarkably useful for theming, density controls, and variant switching.

Note that style queries do not require container-type to be set. Any element can serve as a style query container — containment is only needed for dimensional queries. This makes style queries zero-cost to adopt.

/* No container-type needed for style queries */
.panel {
  --density: comfortable; /* or compact, spacious */
}

@container style(--density: compact) {
  .panel-item {
    padding: 0.25rem 0.5rem;
    font-size: 0.8125rem;
    gap: 0.25rem;
  }
}

@container style(--density: spacious) {
  .panel-item {
    padding: 1rem 1.5rem;
    font-size: 1.125rem;
    gap: 1rem;
  }
}

5. CSS Subgrid

CSS Grid revolutionized web layout, but it had a significant limitation: grid tracks were defined on the grid container, and only direct children participated in those tracks. Grandchildren and deeper descendants created their own independent grids, making it impossible to align nested content to the outer grid.

This caused a persistent visual problem. Imagine a row of cards, each containing a title, description, and button. If one card has a longer title, its description and button shift down — but the other cards' content doesn't follow suit. The cards' internal elements are misaligned across the row because each card has its own independent grid.

Subgrid solves this by letting a grid item's children participate in the parent grid's track sizing. Instead of defining new tracks, you write grid-template-columns: subgrid or grid-template-rows: subgrid, and the item adopts its parent's tracks for that axis.

/* Parent grid defines the columns */
.card-grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 1.5rem;
}

/* Each card spans 1 column but uses subgrid for rows */
.card {
  display: grid;
  grid-row: span 3; /* occupy 3 parent rows */
  grid-template-rows: subgrid; /* adopt parent's row tracks */
  gap: 0; /* can override gap independently */
}

/* Now .card > title, .card > description, .card > button
   all align across cards because they share row tracks */

The key insight is that subgrid makes the parent grid's track sizing consider all participating content. If Card A has a tall title, the title row expands for all cards, keeping descriptions and buttons aligned. This was previously impossible without fixed heights or JavaScript measurement.

Subgrid works on either axis independently. You can subgrid columns while defining your own row tracks, or vice versa. You can even subgrid both axes simultaneously for full alignment inheritance.

Why Subgrid Matters

Before subgrid, developers used workarounds like setting fixed heights on card sections, using Flexbox with flex-grow (which pushes content down but doesn't truly align), or resorting to JavaScript layout measurement. Subgrid provides a pure CSS solution that's responsive, accessible, and performant. It completes the Grid specification's promise of two-dimensional layout control.

Subgrid Adoption Trade-offs

Subgrid is powerful, but it creates tight coupling between parent and child grid definitions. When a child uses grid-template-rows: subgrid, its internal layout is governed by the parent's row tracks. This means the child component cannot be independently deployed into a different grid context without ensuring the parent provides the same track structure. A PE7 uses subgrid strategically: it excels for alignment consistency in scenarios like form label/input grids, card grids where headers/bodies/footers must align, and data tables. But avoid subgrid when components need to be independently portable across different layout contexts — for example, a widget that might appear in a grid dashboard today but a flex sidebar tomorrow. In those cases, the component should own its own grid definition so it remains self-contained. The decision is architectural: subgrid trades component independence for cross-component visual alignment.

6. Subgrid Form Layout

Forms are one of the most compelling use cases for subgrid. A common design pattern is a two-column form where labels sit in the left column and inputs in the right. With traditional CSS, you either wrap each label-input pair in a row container (adding markup) or use a flat grid (which can't handle grouped fieldsets well).

Subgrid lets you structure your form semantically — using <fieldset> elements for logical grouping — while still aligning all labels and inputs to a single parent grid. Each fieldset becomes a subgrid item that inherits the parent's column tracks:

.form-grid {
  display: grid;
  grid-template-columns: [label] max-content [input] 1fr;
  gap: 1rem 1.5rem;
  align-items: baseline;
}

.form-grid fieldset {
  display: grid;
  grid-column: 1 / -1; /* span full width */
  grid-template-columns: subgrid; /* inherit parent columns */
  gap: 0.75rem 1.5rem;
}

.form-grid label {
  grid-column: label;
  justify-self: end;
}

.form-grid input,
.form-grid select,
.form-grid textarea {
  grid-column: input;
}

This approach gives you the best of both worlds: semantic, accessible form markup with <fieldset> and <legend> elements, and pixel-perfect visual alignment across all form groups. The label column auto-sizes to the widest label across all fieldsets, keeping everything aligned.

You can extend this pattern with named grid lines for even more clarity, and combine it with container queries so the form switches to a stacked layout in narrow containers.

7. Combining Container Queries + Subgrid

The true power of modern CSS layout emerges when you combine container queries with subgrid. Container queries let components adapt their internal layout to available space, while subgrid lets them participate in their parent's layout alignment. Together, they create a component system that is simultaneously self-aware and context-aware.

Consider a dashboard widget system. The overall dashboard uses a grid layout. Each widget panel uses subgrid to align its header, content, and footer rows with sibling panels. Meanwhile, container queries let each panel's content adapt: a chart widget might switch from a full chart to a sparkline in narrow containers, or a stats panel might stack its metrics vertically when space is tight.

/* Dashboard grid */
.dashboard {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(300px, 1fr));
  grid-auto-rows: auto;
  gap: 1.5rem;
}

/* Each widget uses subgrid for row alignment */
.widget {
  display: grid;
  grid-row: span 3;
  grid-template-rows: subgrid;
  container-type: inline-size; /* also a container for CQ */
}

/* Widget content adapts to its container */
@container (width < 350px) {
  .widget__stats {
    flex-direction: column;
    font-size: 0.875rem;
  }
}

@container (width >= 350px) {
  .widget__stats {
    flex-direction: row;
    font-size: 1rem;
  }
}

This pattern scales beautifully. You can nest containers within subgrid items, creating a hierarchy where each level handles its own concerns: the grid manages macro-level alignment, subgrid ensures cross-component consistency, and container queries handle micro-level adaptation.

Another powerful combination is using style queries with subgrid. A parent can set --layout: dense, and subgrid children can respond by tightening their internal spacing while maintaining row alignment with siblings. The visual consistency of subgrid combined with the adaptability of container queries creates components that feel alive and responsive to their environment.

8. Name-Only Container Queries

Traditionally, @container rules require a size or style condition — you ask "is this container wider than 400px?" or "does it have --theme: dark?" But a new pattern has landed across all browsers (Chrome, Firefox 149, Safari 26.4): name-only container queries. With this feature, you can match a container by name alone, without specifying any size or style condition.

This simplifies targeting dramatically. Instead of writing a condition that must evaluate to true, you simply reference the container name. Any element inside a container with that name will match, allowing you to apply styles purely based on containment context.

/* Name-only: match by container-name alone, no size/style condition needed */
.widget {
  container-name: --widget;
  container-type: inline-size;
}

@container --widget {
  .inner {
    /* matches any element inside a --widget container */
    padding: 1rem;
    border: 1px solid #e2e8f0;
    border-radius: 8px;
  }
}

/* Practical example: scope styles to a named region */
.sidebar {
  container-name: --sidebar;
  container-type: inline-size;
}

.main-content {
  container-name: --main;
  container-type: inline-size;
}

/* Style components differently based on which named container they live in */
@container --sidebar {
  .nav-link {
    font-size: 0.875rem;
    padding: 0.5rem;
  }
}

@container --main {
  .nav-link {
    font-size: 1rem;
    padding: 0.75rem 1.25rem;
  }
}

The key insight: name-only queries let you apply styles just by being inside a named container, without needing a size or style condition. This is particularly useful for component libraries where you want to scope styles to specific regions of your layout (sidebar, header, modal) without relying on class-based overrides or complex selectors.

Why Name-Only Queries Matter

Before this feature, if you wanted to style a component differently when it appeared inside a sidebar versus main content, you either needed modifier classes (.card--sidebar) or had to combine the container name with an arbitrary size condition. Name-only queries remove that friction — the container's name itself becomes the condition. This makes your CSS more declarative: "if I am inside a --sidebar container, use these styles" with no additional logic required.

Challenge: Adaptive Dashboard with Subgrid

Build a dashboard where each widget panel uses container queries to adapt its content, and the overall grid uses subgrid for alignment. Requirements:

  1. Create a dashboard grid with repeat(auto-fit, minmax(280px, 1fr)) columns.
  2. Each widget panel should span 3 rows and use grid-template-rows: subgrid to align header, body, and footer rows across all panels.
  3. Set each widget panel as a containment context.
  4. Use @container queries inside each widget:
    • Below 300px: show a minimal summary view.
    • 300px–450px: show a standard view with key metrics.
    • Above 450px: show a detailed view with charts or tables.
  5. Add style queries: set --widget-theme: dark on some panels and use @container style(--widget-theme: dark) to apply dark styling.
  6. Ensure all widget headers, bodies, and footers align visually across the row.

Hints

  • The grid container needs grid-auto-rows to define row heights that subgrid items can adopt.
  • Each widget needs both display: grid; grid-template-rows: subgrid; and container-type: inline-size;.
  • Use named containers to prevent inner container queries from accidentally targeting the wrong ancestor.
  • Test by resizing the viewport — as columns wrap, each widget's container query breakpoints fire independently.
