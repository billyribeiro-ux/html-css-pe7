Understanding Space

Master the box model, display types, positioning, and stacking to control how elements occupy and share space.

1. The Box Model

Every element in CSS is a rectangular box. The box model describes how the size of that box is calculated using four layers: content, padding, border, and margin. Understanding this model is essential because it determines how much space every element occupies on the page and how elements relate to each other spatially.

The content area holds the actual text, images, or child elements. Padding is the space between the content and the border — it is inside the element and takes on the element's background color. Border wraps around the padding and content. Margin is the space outside the border that separates the element from its neighbors. Margins are transparent and can collapse (adjacent vertical margins merge into the larger of the two).

By default, CSS uses content-box sizing: when you set width: 300px, that is the width of the content only. Padding and border are added on top, making the total rendered width larger. This often catches beginners off guard. The border-box model changes this: width: 300px includes padding and border, so the content shrinks to fit. Most modern CSS resets apply box-sizing: border-box to all elements.

The difference between the two models becomes critical when building layouts. With content-box, adding padding to a 50% width element pushes it past 50% of its container, breaking side-by-side layouts. With border-box, padding is absorbed into the width, making percentage-based layouts predictable and reliable.

Why Use border-box?

The border-box model makes CSS math intuitive. When you say an element is width: 50%, it is exactly 50% of its parent — padding and border included. This is why nearly every CSS framework and reset stylesheet includes *, *::before, *::after { box-sizing: border-box; }. It prevents countless layout bugs and makes responsive design far simpler.

Box Model Code

/* Apply border-box globally (recommended) */
*, *::before, *::after {
  box-sizing: border-box;
}

/* Box model properties */
.card {
  width: 300px;           /* content width (or total with border-box) */
  padding: 20px;          /* inner spacing */
  border: 2px solid #ccc; /* visible border */
  margin: 16px;           /* outer spacing */
}

/* Margin shorthand: top right bottom left */
.element {
  margin: 10px 20px 10px 20px;
  /* Or: margin: 10px 20px; (vertical | horizontal) */
  /* Or: margin: 10px; (all sides) */
}

Margin Collapse

Margin collapse is one of the most counterintuitive behaviors in CSS. When two vertical margins meet, they do not add together — instead, they collapse into a single margin equal to the larger of the two. This only happens with vertical (top/bottom) margins in block layout; horizontal margins never collapse.

There are three situations where margin collapse occurs:

Adjacent siblings: When two block-level elements are stacked vertically, the bottom margin of the first and the top margin of the second collapse into one. If the first element has margin-bottom: 30px and the second has margin-top: 20px, the space between them is 30px (not 50px).

Parent and first/last child: If there is no padding, border, or inline content separating a parent's top margin from its first child's top margin, those margins collapse. The child's margin effectively "leaks out" of the parent. The same applies to the bottom margin of a parent and its last child.

Empty blocks: If a block element has no height, padding, border, or content, its own top and bottom margins collapse into a single margin.

Margin Collapse in Action

/* Adjacent sibling collapse */
.paragraph {
  margin-top: 20px;
  margin-bottom: 30px;
}
/* Two .paragraphs stacked: gap between them is 30px, not 50px */

/* Parent-child collapse: the h2 margin leaks out of .card */
.card {
  /* no padding or border on top */
}
.card h2 {
  margin-top: 24px;
  /* This 24px pushes the entire .card down, not the h2 inside it */
}

/* Empty block collapse */
.spacer {
  margin-top: 40px;
  margin-bottom: 40px;
  /* With no content/padding/border, total space contributed is 40px */
}

There are several reliable ways to prevent margin collapse:

Preventing Margin Collapse

/* 1. Add padding or border to the parent */
.card {
  padding-top: 1px;       /* even 1px prevents collapse */
  /* or: border-top: 1px solid transparent; */
}

/* 2. Use overflow (creates a new block formatting context) */
.wrapper {
  overflow: hidden;        /* or overflow: auto */
}

/* 3. Use display: flow-root (modern, purpose-built) */
.container {
  display: flow-root;     /* creates BFC without side effects */
}

/* 4. Flexbox/Grid parents never have collapsing margins */
.flex-parent {
  display: flex;
  flex-direction: column;  /* children's margins won't collapse */
}

Why Does Margin Collapse Exist?

Margin collapse was designed for document flow — paragraphs of text. Without it, the spacing between two paragraphs that each have margin: 1em 0 would be 2em, which looks too wide. Collapsing gives you consistent 1em gaps. However, when building component-based layouts, this behavior often causes unexpected spacing. That is why many developers use padding or flexbox gaps instead of margins for component spacing — these never collapse.

2. Display Types

The display property is one of the most important in CSS. It determines how an element participates in the document flow — whether it takes up a full row, sits beside other elements, or is removed from the flow entirely. The three foundational display values are block, inline, and inline-block.

Block elements take up the full width available and start on a new line. They stack vertically. You can set width, height, margin, and padding on all sides. Examples include <div>, <p>, <h1>, and <section>. Block is the default display for most structural elements.

Inline elements flow within text, taking up only as much width as their content. They sit side by side on the same line. You cannot set width or height on inline elements, and vertical margins have no effect. Horizontal padding and margins work but do not push other lines away vertically. Examples include <span>, <a>, <strong>, and <em>.

Inline-block is the hybrid: elements flow inline (sitting next to each other) but accept width, height, and vertical margins like block elements. This is useful for things like navigation links that need a set size and padding but should sit side by side.

Display Types

/* Block: full width, stacks vertically */
.container { display: block; }

/* Inline: flows with text, no width/height */
.tag { display: inline; }

/* Inline-block: flows inline, but accepts dimensions */
.nav-link {
  display: inline-block;
  width: 120px;
  padding: 8px 16px;
}

/* None: completely removed from layout */
.hidden { display: none; }

Additional Display Values

Beyond the three foundational values, CSS offers several more specialized display types that solve specific layout problems:

display: flow-root creates a new block formatting context (BFC). The element itself behaves like a normal block, but its internals are isolated: margins inside it will not collapse with outside margins, and it will fully contain any floated children. Before flow-root existed, developers used overflow: hidden for the same effect, but that had the side effect of clipping content. flow-root was designed specifically for this purpose with no side effects.

display: contents is unusual: it makes the element's own box disappear while keeping all its children in the document. The children behave as if they were direct children of the element's parent. This is useful in flex or grid layouts when you need a semantic wrapper (like a <div> for grouping) but do not want it to create an extra box that disrupts the grid or flex flow.

display: inline-flex creates a flex container that participates in inline flow rather than block flow. The element's children are laid out using flexbox rules internally, but the container itself sits inline with surrounding text and elements, rather than taking up a full row. This is handy for small inline components like tag groups or button sets within a paragraph.

display: inline-grid works the same way but with grid layout internally. The element behaves as an inline-level container whose children are arranged according to CSS Grid rules. Use it when you need a grid-based component to sit within a line of text or alongside other inline elements.

Advanced Display Values

/* flow-root: contain floats, prevent margin collapse */
.clearfix-modern {
  display: flow-root;
}

/* contents: remove the wrapper box, keep children */
.grid-container {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
}
.semantic-group {
  display: contents; /* children act as direct grid items */
}

/* inline-flex: flex container that flows inline */
.tag-list {
  display: inline-flex;
  gap: 4px;
}
.tag-list .tag {
  padding: 2px 8px;
  background: #e0e0e0;
  border-radius: 4px;
}

/* inline-grid: grid container that flows inline */
.mini-grid {
  display: inline-grid;
  grid-template-columns: 1fr 1fr;
  gap: 4px;
}

When to Reach for These Values

Use flow-root whenever you need a block formatting context — typically to stop margin collapse at a component boundary or to contain legacy floats. Use contents sparingly: it is powerful for grid/flex subgrouping, but be cautious with interactive elements like <button> or <a> because removing the box can break accessibility in some browsers. Prefer inline-flex or inline-grid over hacking flex containers into inline behavior with other tricks.

3. Positioning

CSS positioning lets you take elements out of the normal document flow and place them precisely where you want. There are five positioning modes, each with different behavior. Understanding when to use each one is key to building complex layouts, overlays, tooltips, sticky headers, and more.

Static is the default. Elements appear in the normal document flow in the order they appear in the HTML. The top, right, bottom, left, and z-index properties have no effect on statically positioned elements.

Relative positioning keeps the element in the normal flow but lets you offset it from its original position using top, right, bottom, left. The space it originally occupied is preserved — other elements behave as if it had not moved. Relative positioning is most commonly used as a positioning context for absolutely positioned children.

Absolute positioning removes the element from the normal flow entirely. It is positioned relative to its nearest positioned ancestor (any ancestor with a position value other than static). If no positioned ancestor exists, it is positioned relative to the initial containing block (usually the viewport). Other elements ignore its space.

Fixed positioning is like absolute, but relative to the viewport. The element stays in the same position even when the page scrolls. This is perfect for navigation bars, back-to-top buttons, and floating action buttons. Sticky positioning is a hybrid: the element behaves like relative until it reaches a scroll threshold, then it sticks like fixed until its container scrolls past.

Container (position: relative)
static (default)
relative (offset 10px top, 20px left)
absolute (top: 10px, right: 10px)

Positioning Code

/* Relative: offset from normal position */
.parent {
  position: relative;  /* also creates positioning context */
}

/* Absolute: positioned within nearest positioned ancestor */
.tooltip {
  position: absolute;
  top: 100%;
  left: 50%;
  transform: translateX(-50%);
}

/* Fixed: stays in place during scroll */
.navbar {
  position: fixed;
  top: 0;
  left: 0;
  right: 0;
  z-index: 1000;
}

/* Sticky: sticks after scrolling past threshold */
.sidebar-title {
  position: sticky;
  top: 0;
}

Sticky Positioning Gotchas

position: sticky is powerful but has several common pitfalls. The most frequent issue: sticky will not work if any ancestor has overflow: hidden, overflow: scroll, or overflow: auto (unless that ancestor is the intended scroll container). Sticky elements need to find a scrollable ancestor to stick within, and overflow values other than visible on intermediate elements break this chain.

Another gotcha: a sticky element only sticks within the bounds of its parent container. Once the parent scrolls out of view, the sticky child goes with it. This is actually useful — it means sticky section headers naturally unstick when their section ends — but it surprises developers who expect the element to stay fixed indefinitely.

You must also specify at least one of top, right, bottom, or left for sticky to activate. Without a threshold, the browser does not know when to start sticking.

Sticky Positioning Pitfalls

/* This will NOT work — parent has overflow: hidden */
.parent {
  overflow: hidden;    /* breaks sticky for all descendants */
}
.parent .sticky-header {
  position: sticky;
  top: 0;              /* will be ignored */
}

/* Fix: remove overflow from the parent, or restructure */
.parent {
  overflow: visible;   /* sticky now works */
}

/* Sticky within a specific section */
.section {
  min-height: 600px;   /* sticky child unsticks when section ends */
}
.section-heading {
  position: sticky;
  top: 60px;           /* e.g., below a fixed navbar */
}

Containing Blocks & Absolute Positioning

When you use position: absolute, the element is positioned relative to its containing block. For most cases, the containing block is the nearest ancestor that has position set to anything other than static (i.e., relative, absolute, fixed, or sticky).

However, there are other properties that establish a containing block for absolutely positioned descendants: transform, filter, perspective, will-change (when referencing transform/filter/perspective), and contain: paint or contain: layout. This catches many developers off guard — adding a simple transform: translateZ(0) to an ancestor for performance reasons can suddenly change where your absolutely positioned elements anchor.

If no positioned ancestor exists at all, the absolutely positioned element is placed relative to the initial containing block, which corresponds to the viewport (specifically, the <html> element's content area).

Containing Block Behavior

/* Standard containing block: nearest positioned ancestor */
.card {
  position: relative;   /* containing block for .badge */
}
.card .badge {
  position: absolute;
  top: -8px;
  right: -8px;
}

/* Surprise containing block: transform on an ancestor */
.animated-wrapper {
  transform: scale(1);  /* this now acts as containing block! */
}
.animated-wrapper .tooltip {
  position: absolute;   /* positioned relative to .animated-wrapper */
  /* NOT relative to a position:relative ancestor further up */
}

The inset Shorthand

The inset property is a shorthand for setting top, right, bottom, and left in a single declaration. It follows the same clockwise order as margin and padding: top, right, bottom, left. A single value sets all four sides equally, which is especially useful for full-coverage overlays.

The inset Shorthand

/* Without inset */
.overlay {
  position: fixed;
  top: 0;
  right: 0;
  bottom: 0;
  left: 0;
}

/* With inset — identical result */
.overlay {
  position: fixed;
  inset: 0;            /* all four sides set to 0 */
}

/* inset with different values: top right bottom left */
.panel {
  position: absolute;
  inset: 10px 20px 10px 20px;
}

/* Two values: vertical | horizontal */
.centered-box {
  position: absolute;
  inset: 2rem 4rem;   /* top/bottom: 2rem, left/right: 4rem */
}

4. Overflow

When content is larger than its container, the overflow property controls what happens. By default, content overflows visibly, spilling out of its box. This is often undesirable — you may want to clip the excess, add scrollbars, or show scrollbars only when needed.

visible (default) lets content overflow the box without clipping. hidden clips content at the box boundary — anything beyond is invisible and unreachable. scroll always shows scrollbars, even when the content fits. auto shows scrollbars only when the content actually overflows, which is usually the best choice for scrollable containers.

You can control horizontal and vertical overflow independently with overflow-x and overflow-y. This is useful for wide tables that need horizontal scrolling but not vertical, or for chat windows that need vertical scrolling only.

Overflow also creates a new block formatting context, which prevents margin collapsing and contains floated children. Setting overflow: hidden on a parent is a classic technique for containing floats, though modern layout methods (flexbox and grid) have largely replaced this pattern.

Overflow Behaviors

overflow: visible

This content is taller than its container. With overflow: visible, it spills out beyond the boundary of the box and overlaps whatever comes below it.

overflow: hidden

This content is taller than its container. With overflow: hidden, the excess content is clipped and completely invisible. Users cannot scroll to see it.

overflow: scroll

This content is taller than its container. With overflow: scroll, scrollbars always appear, even if the content fits. This can look odd on short content but guarantees scrollability.

overflow: auto

This content is taller than its container. With overflow: auto, scrollbars appear only when needed. This is the most common and user-friendly option for scrollable areas.

Overflow Code

/* Hide overflow */
.card-image {
  overflow: hidden;
  border-radius: 12px;
}

/* Scrollable container */
.chat-messages {
  overflow-y: auto;
  max-height: 400px;
}

/* Horizontal scroll for wide content */
.table-wrapper {
  overflow-x: auto;
  overflow-y: hidden;
}

5. Z-Index & Stacking

While most CSS layout is two-dimensional (horizontal and vertical), the z-index property controls the third dimension: the stacking order of overlapping elements. Elements with higher z-index values appear in front of elements with lower values. But z-index only works on positioned elements (anything other than position: static).

The concept of stacking contexts is crucial. A stacking context is a three-dimensional conceptualization of HTML elements along an imaginary z-axis. When an element creates a new stacking context, all of its children are stacked within that context. A z-index of 9999 on a child will never appear above a sibling of its parent that has a higher stacking order.

Stacking contexts are created by several CSS properties: any positioned element with a z-index value other than auto, elements with opacity less than 1, elements with transform, filter, or will-change properties, and flex/grid children with z-index values. Understanding this prevents the common confusion of "why is my z-index: 99999 not working?"

In practice, use a structured z-index scale: define layers in your CSS (e.g., base content at 1, dropdowns at 100, modals at 200, tooltips at 300, notifications at 400). This prevents the arms race of ever-increasing z-index values and keeps your stacking predictable.

Why Z-Index Values Should Be Systematic

Without a system, z-index values escalate wildly: one developer uses 10, another uses 100 to go above it, then someone uses 9999. Soon you have z-index: 2147483647 (the max 32-bit integer) and nowhere to go. Define a layer system with clear ranges: base (1-9), navigation (10-19), dropdowns (20-29), modals (30-39), tooltips (40-49). This creates order and makes debugging effortless.

Z-Index System

/* Define z-index layers with custom properties */
:root {
  --z-base: 1;
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-modal-backdrop: 300;
  --z-modal: 400;
  --z-tooltip: 500;
  --z-notification: 600;
}

.dropdown-menu {
  position: absolute;
  z-index: var(--z-dropdown);
}

.modal-overlay {
  position: fixed;
  z-index: var(--z-modal-backdrop);
}

.modal {
  position: fixed;
  z-index: var(--z-modal);
}

What Creates a Stacking Context?

Many CSS properties silently create new stacking contexts. When a new stacking context is formed, all descendants are stacked within it — their z-index values only compete with siblings inside that context, not with elements outside it. This is the root cause of most "my z-index is not working" bugs.

The following properties and conditions create a new stacking context:

  • position: absolute or position: relative with a z-index value other than auto
  • position: fixed or position: sticky (always)
  • opacity with a value less than 1
  • transform with any value other than none
  • filter with any value other than none
  • will-change specifying transform, opacity, or similar properties
  • isolation: isolate (explicitly creates a stacking context)
  • Flex and grid children with a z-index value other than auto
  • mix-blend-mode with any value other than normal
  • contain: layout or contain: paint

Stacking Context Traps

/* TRAP: opacity creates a stacking context */
.parent {
  position: relative;
  opacity: 0.99;        /* new stacking context! */
}
.parent .dropdown {
  position: absolute;
  z-index: 9999;        /* only competes within .parent's context */
  /* Cannot appear above elements outside .parent with z-index >= 1 */
}

/* TRAP: transform creates a stacking context */
.card {
  transform: translateY(0); /* new stacking context */
}

/* FIX: use isolation to intentionally scope stacking */
.component {
  isolation: isolate;   /* explicit, self-documenting */
}
/* Now z-index values inside .component are scoped to it */

/* Debugging tip: if z-index isn't working, check ALL ancestors
   for any property from the list above */

Why Stacking Contexts Matter for Component Design

In component-based architectures, stacking contexts can be both a problem and a tool. An unintended stacking context on a card component can trap its dropdown menus beneath other cards. But intentional stacking contexts (using isolation: isolate) let you scope a component's z-index values so they do not leak out and conflict with the rest of the page. When building reusable components, consider adding isolation: isolate to the component root — it is the most explicit and side-effect-free way to create a stacking context.

Challenge: Layered Card Stack

Create a visually striking card stack effect:

  • Create 5 cards that overlap each other, each offset slightly to the right and down from the one below it.
  • Each card should have an increasing z-index so the last card appears on top.
