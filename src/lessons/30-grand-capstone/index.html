1. Project Overview

The Assignment

Build the PE7 Agency Landing Page

Design and code a multi-section, production-quality landing page for PE7 Creative Agency — a fictional digital design studio. The page must demonstrate mastery of every major CSS feature covered across all nine levels of this course. It is a single HTML file with a single CSS file. No frameworks. No build tools. No JavaScript. Pure HTML and CSS.

This is not a follow-along tutorial. There are no step-by-step instructions. You are given a detailed specification, a requirements checklist, an architecture guide, and a starter template. The rest is yours to build.

What you are being evaluated on: Not pixel-perfect design — creative interpretation is encouraged. You are evaluated on technique coverage, code architecture, accessibility, and performance awareness. A visually simple page that demonstrates every technique correctly will score higher than a flashy page that skips half the checklist.

PE7 Principle: Leave a Trail of Reasoning, Not Just Code

Before you write a single line of CSS, a PE7 engineer writes an architecture decision record — even if it is just comments at the top of the file. Why BEM-style naming over utility classes? Because your team has four people and readability at the component boundary matters more than terseness. Why oklch() over hsl()? Because perceptual uniformity means your programmatically generated tints actually look evenly spaced to human eyes, and you need relative color syntax for the hover states. Why container queries on the service cards but media queries on the page layout? Because the service cards get reused in a sidebar context where viewport width is irrelevant, but the overall page grid genuinely depends on the viewport. Every decision has a reason. A PE7 does not choose tools because they are new or trendy — they choose them because the constraints of the project make that tool the right one. Document those constraints. Six months from now, when someone asks “why not Tailwind?” or “why not HSL?”, the answer should already be in the codebase, not trapped in your memory.

The tone is confident but approachable — they let their work speak louder than their words.

PE7 Principle: Set a Performance Budget Before You Build

A PE7 engineer does not discover performance problems after launch — they define constraints before the first commit. Here is your budget: the total CSS for this landing page should stay under 50KB compressed. Beyond that threshold, you are shipping styles that actively harm the user experience, because CSS is render-blocking — every byte of it delays first paint, even the bytes the current page never uses. That unused .testimonial-card-variant-b class you never deleted? It is still forcing the browser to parse and hold it in memory before painting a single pixel. This is why @layer is not just an organizational nicety — it is a performance architecture. Layers let you reason about what loads and in what order. For a single-page capstone, one file is fine. But on a production site, you would split critical above-the-fold CSS (your reset, base, and layout layers) into an inline <style> block, then load the components and utilities layers asynchronously. The point is not to prematurely optimize — it is to know the cost of every decision. content-visibility: auto on your below-fold sections is worth 3 rubric points, yes, but more importantly, it can cut rendering work by 50% on long pages. contain: layout style paint tells the browser a subtree is independent, enabling it to skip re-layout work. These are not tricks. They are how a PE7 thinks about CSS: every property has a rendering cost, and you should be able to justify paying it.

4. Architecture Guide

Good CSS architecture is the difference between a project you can maintain and one that collapses under its own weight. Follow these guidelines for your capstone.

PE7 Principle: Progressive Enhancement Is Architecture, Not a Fallback Strategy

This capstone specifies “No JavaScript. Pure HTML and CSS.” That is not a constraint imposed to make the project harder — it is a design philosophy. A PE7 engineer understands that each layer of the web platform owns specific responsibilities: HTML owns structure and semantics, CSS owns presentation and interaction feedback, and JavaScript owns behavior that neither layer can express. When you build the testimonials accordion with <details> and ::details-content, that accordion works the instant the HTML parses — before a single stylesheet loads. The CSS makes it beautiful and animated, but the core functionality is already there. When you build the portfolio filter with :has() and checkbox state, that filter works because HTML checkboxes have built-in state and CSS can read it. You are not “faking” interactivity — you are building it in the right layer. This matters at scale. JavaScript fails silently in hostile environments: corporate proxies strip it, ad blockers break it, CDNs go down. HTML and CSS are resilient by default. A PE7 builds the core experience in the layers that cannot fail, then enhances with the layers that might. That is not pessimism. That is engineering.

Layer Order

Declare your layers at the very top of your CSS file, before any other rules:

CSS

/* Layer declaration — order determines priority */
@layer reset, base, layout, components, utilities;

/* Optional: functions and mixins before layers */
@function --space(--n) {
  result: calc(var(--n) * 0.25rem);
}

@layer reset {
  /* Box-sizing, margin/padding reset, etc. */
}

@layer base {
  /* @property registrations */
  /* Design tokens (custom properties on :root) */
  /* Typography defaults */
  /* Color scheme and prefers-* queries */
}

@layer layout {
  /* Page-level layout: nav, main, footer grid */
  /* Section spacing and max-widths */
}

@layer components {
  /* Individual component styles: cards, buttons,
     accordions, forms, tooltips */
  /* Use CSS nesting inside each component block */
}

@layer utilities {
  /* Utility classes: .visually-hidden, .gradient-text */
  /* Override-level helpers */
}

Custom Property Naming Convention

Adopt a consistent naming scheme. The recommended convention for PE7 is a two-tier system:

Global Tokens (Tier 1)

--color-indigo-500
--color-coral-400
--space-md
--font-display
--radius-lg

Raw design values. Never used directly in component styles.

↓

Semantic Tokens (Tier 2)

--clr-bg
--clr-surface
--clr-text
--clr-accent
--btn-radius

Meaningful aliases. These are what components reference. When the theme changes, only Tier 2 values update.

CSS

@layer base {
  :root {
    /* Tier 1: raw palette */
    --color-indigo-500: oklch(0.55 0.24 280);
    --color-indigo-400: oklch(0.65 0.22 280);
    --color-coral-500:  oklch(0.65 0.22 25);
    --color-mint-500:   oklch(0.72 0.15 175);
    --color-slate-900:  oklch(0.15 0.01 260);
    --color-slate-800:  oklch(0.20 0.015 260);

    /* Tier 2: semantic mapping */
    --clr-bg:      var(--color-slate-900);
    --clr-surface: var(--color-slate-800);
    --clr-text:    oklch(0.93 0.01 260);
    --clr-accent:  var(--color-indigo-500);
    --clr-cta:     var(--color-coral-500);
    --clr-success: var(--color-mint-500);
  }

  @media (prefers-color-scheme: light) {
    :root {
      --clr-bg:      oklch(0.97 0.005 260);
      --clr-surface: oklch(0.99 0.002 260);
      --clr-text:    oklch(0.20 0.02 260);
    }
  }
}

File Organization Hints

Even though you are working in a single CSS file, organize it as if it were multiple files. Use clear comment headers to separate each layer and each component block within layers:

CSS

/* ==============================================
   PE7 AGENCY LANDING PAGE
   Grand Capstone Project
   ============================================== */

@layer reset, base, layout, components, utilities;

/* ========= RESET ========= */
@layer reset { /* ... */ }

/* ========= BASE ========= */
@layer base { /* tokens, @property, prefers-* */ }

/* ========= LAYOUT ========= */
@layer layout { /* nav, main, footer structure */ }

/* ========= COMPONENTS ========= */
@layer components {
  /* -- Hero -------------------------------- */
  /* -- About ------------------------------- */
  /* -- Services (masonry) ------------------ */
  /* -- Portfolio (subgrid) ----------------- */
  /* -- Testimonials (accordion) ------------ */
  /* -- Contact (form) ---------------------- */
  /* -- Footer ------------------------------ */
  /* -- Scroll progress bar ----------------- */
  /* -- Tooltips (anchor-positioned) -------- */
  /* -- Popover ----------------------------- */
}

/* ========= UTILITIES ========= */
@layer utilities { /* .visually-hidden, .gradient-text */ }

/* ========= REDUCED MOTION ========= */
@media (prefers-reduced-motion: reduce) { /* ... */ }

Nesting Conventions

Nest component children inside their parent block. Keep nesting no deeper than three levels. Use & for pseudo-classes, pseudo-elements, and modifier states:

CSS

.service-card {
  background: var(--clr-surface);
  border-radius: var(--radius-lg);
  container-type: inline-size;

  & .card-icon {
    color: var(--clr-accent);
    transition: transform 0.3s ease;
  }

  &:hover {
    box-shadow: var(--shadow-lg);

    & .card-icon {
      transform: scale(1.1);
    }
  }

  &:focus-visible {
    outline: 2px solid var(--clr-accent);
    outline-offset: 3px;
  }

  @container (min-width: 400px) {
    display: grid;
    grid-template-columns: auto 1fr;
  }
}

PE7 Principle: The Code Review Checklist You Should Internalize

Before you submit this capstone, review your own CSS the way a PE7 reviews a pull request. Look for specificity creep — if you needed !important or a four-selector chain to override something, your layer architecture has a hole. Look for magic numbers — a margin-block-start: 37px with no comment explaining why 37 and not 36 or 40 is a maintenance trap waiting to break on a different screen. Look for undocumented z-index values — if your tooltip uses z-index: 9999, you have not thought about stacking contexts; define a z-index scale in your tokens (--z-nav: 100, --z-tooltip: 200, --z-modal: 300). Look for missing logical properties — every margin-left is a bug for RTL users; use margin-inline-start. Look for hard-coded colors outside your token system — a raw #6c5ce7 in a component block means your dark/light theme switch will miss it. Look for animations that trigger layout — animating width, height, or top forces the browser to recalculate layout on every frame; use transform and opacity instead, which run on the compositor thread. This is not nitpicking. This is the difference between CSS that survives contact with a real team and CSS that becomes everyone’s least favorite file in the repo.

6. Tips from the PE7 Team

01

Start with the skeleton

Write all your HTML first. Get every section, every landmark, every form element in place before touching CSS. Semantic structure is worth 3 points on its own and makes everything else easier.

02

Declare layers early

Put your @layer declaration on line 1 of your CSS. Add all @property registrations in the base layer before any visual styles. This prevents specificity surprises later.

03

Work section by section

Do not try to implement all 40 techniques at once. Build one section, check off its required techniques, then move to the next. Each completed section is progress you cannot lose.

04

Test reduced motion first

Enable prefers-reduced-motion: reduce in your browser dev tools before adding animations. Build the static version, then layer motion on top. This guarantees your reduced-motion fallback works.

05

Use the checklist as a commit guide

After implementing each technique, open the checklist and confirm it is present. Consider writing a CSS comment near each technique: /* CHECKLIST: @property animation */. This helps during review.

06

Do not over-animate

You need scroll-driven animations and transitions, but the rubric says animations should enhance rather than distract. Subtle reveals and smooth state changes beat flashy pyrotechnics. Restraint is a skill.

PE7 Principle: Maintainability Over Cleverness

You have spent 29 modules learning what CSS can do. Now here is the hardest skill of all: knowing when not to use it. A PE7’s CSS should be boring. That clever one-liner using :has(> :nth-child(3):not(:last-child) ~ *) that saves two lines of CSS but takes five minutes for your teammate to understand? That is tech debt with a bow on it. The goal is not to write the fewest lines — it is to write CSS that a new team member can read, understand, modify, and safely delete without breaking something three sections away. Deletability is an underrated virtue: if you can remove a component’s styles and nothing else on the page shifts, your architecture is working. If removing one class triggers a cascade of layout breaks, you have implicit dependencies that will haunt every future change. Prefer explicit, predictable patterns over clever abstractions. Use @layer so that adding a new component never accidentally overrides an existing one. Use semantic custom property names so the next developer knows what --clr-surface-2 means without reading the token definition. Write the CSS your future self will thank you for, not the CSS that impresses you today.

Remember: You have already built every technique in isolation across modules 1 through 29. This capstone is not about learning something new — it is about combining everything you already know into a single, cohesive project. Trust your training. Ship it.
