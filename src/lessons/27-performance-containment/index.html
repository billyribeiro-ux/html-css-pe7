CSS Performance & Containment

Understand the browser rendering pipeline, isolate layout and paint work with contain and content-visibility, use will-change responsibly, and build interfaces that stay fast at any scale.

1. The Rendering Pipeline

Every time the browser draws your page, it follows a strict sequence of steps. Understanding this pipeline is the foundation of CSS performance work. If you know which stages your CSS changes trigger, you can make informed decisions about what to animate, what to contain, and what to avoid.

The five stages are: Parse, Style, Layout, Paint, and Composite. Each stage depends on the output of the previous one. The later in the pipeline you trigger work, the cheaper the change. The earlier you trigger it, the more downstream work the browser must redo.

Why Reflows Are Expensive

A reflow (also called layout recalculation) happens when the browser must recalculate the geometry of elements. This is expensive because layout is global by default: changing the width of one element can push siblings, shift their children, alter the height of their parent, and cascade through the entire document tree. A single reflow on a complex page can block the main thread for tens of milliseconds, causing visible jank during scrolling or animation.

Containment exists specifically to break this chain. When you contain an element's layout, the browser knows that changes inside that element cannot affect anything outside it, so it can skip the global recalculation and only reflow the contained subtree.

Key Insight: The rendering pipeline is not optional knowledge for performance work. When you see a janky animation, the first question should always be: "Which pipeline stage is this change triggering?" If the answer is "layout," you have found your bottleneck. Move the animation to transform or opacity to keep it in the composite-only lane.

2. The contain Property

The contain property tells the browser that an element's internals are independent from the rest of the document. This is a performance contract: you promise the browser that certain things about this element will not leak outward, and in return the browser can optimize rendering by skipping work it would normally have to do.

There are five individual containment types, plus two shorthand values that combine them.

Individual Containment Types

contain: layout

The element's internal layout does not affect the rest of the page, and vice versa. The element establishes an independent formatting context. Floats inside cannot poke out, and layout changes inside cannot trigger reflows outside.

Use when: You have a widget or component whose internal layout changes frequently (e.g., a live feed, a chat window) and you want to prevent those changes from causing page-wide reflows.

contain: paint

Nothing inside the element can be painted outside its bounds. The element becomes a scroll container clipping boundary and establishes a new stacking context. This lets the browser skip painting descendants when the element is off-screen.

Use when: You have scroll containers, off-screen content, or components with overflow: hidden already applied. Paint containment formalizes what you are already doing and lets the browser skip paint for clipped-away content.

contain: size

The element's size does not depend on its children. You must give it an explicit width and height. The browser can determine the element's size without examining any of its descendants.

Use when: You know the exact dimensions of a container and want the browser to skip measuring its children for sizing. Common with fixed-size card grids, video players, and ad slots.

contain: style

Counters and quotes scoping. Prevents CSS counter increments and named styles inside the element from affecting counters and quotes outside. This is the narrowest containment type.

Use when: You have nested ordered lists or generated content using CSS counters and you want to scope the counter state to a subtree.

Shorthand Values

CSS

/* contain: strict = layout + paint + size + style */
.card-grid .card {
  contain: strict;
  width: 300px;
  height: 400px;
}

/* contain: content = layout + paint + style (no size) */
/* This is the most commonly useful shorthand.
   It lets the element size itself normally based
   on content, but contains everything else. */
.feed-item {
  contain: content;
}

/* You can combine individual values */
.sidebar-widget {
  contain: layout paint;
}

How Containment Skips Work

When you set contain: layout on an element, the browser creates an optimization boundary. During a reflow, if the browser encounters a contained element and determines that the change originates outside the container, it skips the entire contained subtree. Conversely, if the change originates inside the container, the browser knows it does not need to reflow anything outside. This is a bidirectional optimization fence.

3. content-visibility

If contain is a scalpel, content-visibility is a sledgehammer -- in the best way. It allows the browser to skip all rendering work for off-screen elements: no style resolution, no layout, no paint, no compositing. On long pages with hundreds of elements, this can cut initial render time by 50% or more.

content-visibility: auto

This is the headline feature. When an element has content-visibility: auto, the browser will fully render it only when it is near the viewport (using the intersection observer internally). Off-screen elements get contain: layout paint style size applied automatically, and their rendering is deferred entirely.

CSS

/* Skip rendering for off-screen sections */
.page-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}

/* The browser will:
   1. Not render sections far from the viewport
   2. Render them as the user scrolls near
   3. Keep them rendered after they've been seen
   4. Use 500px as placeholder height to
      prevent layout shift */

content-visibility: hidden

This is like display: none but better. The element is hidden and takes no space, but the browser preserves its rendering state. When you make it visible again, there is no re-render cost -- the cached state is reused. This is perfect for tab panels, off-screen slides, and preloaded content.

CSS

/* Hide inactive tabs without destroying state */
.tab-panel {
  content-visibility: hidden;
}

.tab-panel.active {
  content-visibility: visible;
}

/* Compare with display: none --
   display: none destroys the rendering state.
   When you show the element again, the browser
   must redo style, layout, and paint from scratch.
   content-visibility: hidden preserves the cache. */

contain-intrinsic-size

When content-visibility: auto hides an element, the element has zero height by default (because size containment is applied). This causes massive layout shift as sections pop into existence during scroll. The contain-intrinsic-size property gives the browser a placeholder size to use for hidden elements, preventing the shift.

CSS

/* Fixed placeholder height */
.section {
  content-visibility: auto;
  contain-intrinsic-size: 0 600px;
}

/* auto keyword: remember the last rendered height */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
  /* Uses 600px initially, then remembers the
     actual rendered height for future visits */
}

/* Width and height */
.card {
  content-visibility: auto;
  contain-intrinsic-size: 300px 200px;
}

4. will-change

The will-change property is an optimization hint that tells the browser to prepare for a specific kind of change before it happens. When you say will-change: transform, the browser promotes the element to its own compositor layer in advance, so that when the transform actually changes, the browser can handle it entirely in the compositor thread without touching layout or paint.

This sounds like free performance, but it is not. Layer promotion has a cost: each layer consumes GPU memory, and too many layers can actually make things slower. Use will-change surgically, not as a blanket optimization.

What It Does: Layer Promotion

CSS

/* Before animation starts: promote to own layer */
.modal {
  will-change: transform, opacity;
}

/* The browser now:
   1. Creates a separate GPU texture for this element
   2. Rasterizes the element into that texture
   3. When transform/opacity change, it only needs
      to re-composite the layer (no repaint)
   4. The main thread is freed up for other work */

When to Use

CSS

/* GOOD: Apply on hover, before animation starts */
.card {
  transition: transform 0.3s ease;
}
.card:hover {
  will-change: transform;
}
.card:active {
  transform: scale(0.98);
}

/* GOOD: Apply when parent signals an upcoming change */
.sidebar.is-animating .sidebar-content {
  will-change: transform;
}

/* GOOD: Apply via JavaScript right before animation */
/* element.style.willChange = 'transform';
   // ... start animation ...
   // on animation end:
   element.style.willChange = 'auto'; */

When NOT to Use

CSS

/* BAD: On every element "just in case" */
* {
  will-change: transform, opacity;
  /* This promotes EVERYTHING to its own layer.
     Hundreds of layers = GPU memory exhaustion. */
}

/* BAD: On elements that never actually change */
.static-header {
  will-change: transform;
  /* Wastes GPU memory for no benefit. */
}

/* BAD: On too many list items at once */
.list-item {
  will-change: transform;
  /* 500 list items = 500 GPU layers.
     The browser was already optimizing this. */
}

/* BAD: Left on permanently after animation ends */
.modal.closed {
  will-change: transform;
  /* The modal is closed. Remove the hint. */
}

Cleanup Patterns

The best practice is to apply will-change just before an animation starts and remove it when the animation ends. This limits GPU memory usage to only the moments when the optimization is actually needed.

CSS + JavaScript

/* CSS-only cleanup via :hover */
.card {
  transition: transform 0.3s ease;
}
.card:hover {
  will-change: transform;
  transform: translateY(-4px);
}
/* When hover ends, will-change is removed
   automatically because :hover no longer applies */

/* JavaScript cleanup for complex animations */
/* element.addEventListener('mouseenter', () => {
  element.style.willChange = 'transform';
});
element.addEventListener('transitionend', () => {
  element.style.willChange = 'auto';
}); */

Only use will-change when you have measured a jank problem and identified the specific element and property causing it. Apply it just before the animation, remove it after. Never use will-change on more than a handful of elements simultaneously.

5. Paint Containment Patterns

Paint containment is arguably the most practically useful containment type. When you apply contain: paint to an element, you are telling the browser that nothing inside this element will ever be visible outside its bounds. The browser can then skip painting descendants entirely when the element is off-screen, and it can limit repaint areas to just the contained region when something inside changes.

Scroll Containers

Any element with overflow: hidden or overflow: auto is already visually clipping its children. Adding contain: paint makes this explicit to the browser's rendering engine, allowing it to make the same optimization formally rather than heuristically.

CSS

/* Scroll container with paint containment */
.scrollable-feed {
  height: 400px;
  overflow-y: auto;
  contain: paint;
  /* The browser can now skip painting items
     that have scrolled out of view. Without
     containment, it might still paint them
     into the layer "just in case." */
}

/* Infinite scroll list with full containment */
.infinite-list {
  contain: content;
  overflow-y: auto;
  height: 100vh;
}

.infinite-list .item {
  contain: content;
  /* Each item is independently contained.
     Adding a new item at the bottom doesn't
     force a repaint of existing items. */
}

Isolating Repaint Areas

Without containment, when you change the background color of a nested element, the browser may repaint a much larger area than necessary, because it cannot be sure the change does not affect surrounding content (due to filters, blend modes, or overflow). Paint containment guarantees the repaint stays within the element's bounds.

CSS

/* Widget that updates frequently */
.live-ticker {
  contain: paint;
  /* Price updates cause repaints, but they
     are now isolated to just this widget.
     The rest of the page is untouched. */
}

/* Chat message list */
.chat-messages {
  contain: paint;
  overflow-y: auto;
}

.chat-message {
  contain: content;
  /* New messages only repaint themselves,
     not the entire chat container. */
}

Containment for Infinite Scroll

Infinite scroll lists are the poster child for containment. As the list grows to hundreds or thousands of items, rendering performance degrades without containment because every new item triggers style recalculation and potentially layout for the entire list. With containment on each item, the browser processes each addition in isolation.

6. CSS Performance Best Practices

Beyond containment and will-change, there are broader CSS performance patterns that matter in production. Some are well-known, some are widely misunderstood, and some are only relevant at scale. This section separates the real optimizations from the myths.

Avoiding Layout Thrashing

Layout thrashing happens when JavaScript repeatedly reads layout properties and then writes style changes in an interleaved pattern, forcing the browser to perform a synchronous layout calculation on every read. This is not a CSS problem per se, but CSS properties are what trigger it.

JavaScript (the problem)

// BAD: Read-write-read-write pattern
// Each .offsetHeight read forces a synchronous layout
for (const el of elements) {
  const h = el.offsetHeight;    // FORCED LAYOUT
  el.style.height = h + 10 + 'px'; // invalidate
}

// GOOD: Batch reads, then batch writes
const heights = elements.map(el => el.offsetHeight);
elements.forEach((el, i) => {
  el.style.height = heights[i] + 10 + 'px';
});

Efficient Selectors: Myth vs Reality

You have probably heard that CSS selector performance matters -- that deeply nested selectors are slow, that * is expensive, that you should use BEM or flat selectors for speed. In modern browsers, this is mostly a myth. Selector matching is extraordinarily fast (microseconds per element). The browser reads selectors right-to-left and uses bloom filters and hash maps for matching.

Where selectors do matter is in style recalculation scope. When a class changes on one element, the browser must check which elements' styles are invalidated. With a flat selector like .card-title, invalidation is simple. With a complex selector like .sidebar:has(.nav-item:hover) ~ .main .card:nth-child(odd) .title, the browser must evaluate a wider scope.

Effective Optimizations

  • Use transform and opacity for animations (composite-only)
  • Apply contain: content to independent components
  • Use content-visibility: auto on long scrollable lists
  • Batch DOM reads and writes to avoid layout thrashing
  • Avoid animating box-shadow -- animate a pseudo-element's opacity instead
  • Reduce the scope of style recalculations with containment
  • Use the auto keyword with contain-intrinsic-size

Common Myths

  • "Avoid descendant selectors for performance" -- negligible in modern engines
  • "IDs are faster than classes" -- difference is unmeasurable
  • "Use will-change on everything for speed" -- causes memory bloat
  • "Inline styles are faster" -- style recalculation is the same
  • "Fewer CSS rules = faster rendering" -- true only at extreme scale
  • "GPU acceleration is always better" -- layer management has overhead

Composite-Only Animations

The golden rule of CSS animation performance: if you can express the animation using only transform and opacity, the browser can run it entirely on the compositor thread, off the main thread. This means the animation will stay smooth even if the main thread is busy running JavaScript.

CSS

/* BAD: Animating left triggers layout on every frame */
.slide-in {
  animation: slide-bad 0.3s ease;
}
@keyframes slide-bad {
  from { left: -100%; }
  to   { left: 0; }
}

/* GOOD: Animating transform stays in compositor */
.slide-in {
  animation: slide-good 0.3s ease;
}
@keyframes slide-good {
  from { transform: translateX(-100%); }
  to   { transform: translateX(0); }
}

/* BAD: Animating box-shadow repaints every frame */
.card:hover {
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
  transition: box-shadow 0.3s ease;
}

/* GOOD: Animate a pseudo-element's opacity instead */
.card {
  position: relative;
}
.card::after {
  content: "";
  position: absolute;
  inset: 0;
  border-radius: inherit;
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
  opacity: 0;
  transition: opacity 0.3s ease;
  pointer-events: none;
}
.card:hover::after {
  opacity: 1;
}

Avoiding filter on Scroll

CSS filter effects like blur(), brightness(), and saturate() are GPU-accelerated, but they still require the browser to re-render the affected pixels. Applying filters to elements that change frequently during scroll (like a sticky header with a backdrop blur) can cause dropped frames on lower-end devices.

CSS

/* CAUTION: blur filter recalculated during scroll */
.sticky-header {
  position: sticky;
  top: 0;
  backdrop-filter: blur(10px);
  /* This works fine on powerful devices but can
     cause jank on mid-range phones. Test on real
     hardware before shipping. */
}

/* SAFER: Solid background with opacity */
.sticky-header {
  position: sticky;
  top: 0;
  background: rgba(15, 17, 23, 0.95);
  /* No filter recalculation during scroll. */
}

7. Measuring Performance

All of the techniques in this module are only useful if you can measure their impact. Chrome DevTools provides several specialized panels for CSS performance analysis. Knowing which tool to reach for is as important as knowing the optimization itself.

Chrome DevTools Performance Panel

Record a performance trace while interacting with your page. The trace breaks down time spent in each pipeline stage:

  • Recalculate Style (purple): Time spent matching CSS selectors and computing styles. If this is high, look at your selector complexity and containment boundaries.
  • Layout (purple): Time spent calculating geometry. If this is high, look for layout thrashing or missing containment on frequently-changing elements.
  • Paint (green): Time spent filling pixels. If this is high, look for large repaint areas, animated box-shadow, or filters applied to large elements.
  • Composite Layers (green): Time spent assembling layers. If this is high, you may have too many promoted layers (over-use of will-change).

Paint Flashing

In the DevTools Rendering panel, enable Paint flashing. This highlights every area that gets repainted in green. Ideally, during a scroll or animation, you should see minimal green flashing. Large green areas on every frame indicate repaint waste that containment can fix.

Layout Shift Visualization

Also in the Rendering panel, enable Layout Shift Regions. This highlights elements that move unexpectedly, which contributes to the Cumulative Layout Shift (CLS) metric. contain-intrinsic-size with content-visibility: auto directly addresses this.

Layers Panel

The Layers panel (under More Tools) shows every compositor layer, its memory usage, and why it was promoted. This is essential for debugging will-change usage. If you see dozens of layers you did not intend to create, you have an over-promotion problem.

Performance Audit Checklist

Record a Performance trace during scroll. Are there long Layout tasks (>16ms)?
Enable Paint Flashing. Are large areas repainting on scroll or hover?
Check the Layers panel. Are there more than 20 promoted layers?
Enable Layout Shift Regions. Are elements jumping during load or scroll?
Run a Lighthouse audit. Is CLS below 0.1? Is Total Blocking Time under 200ms?
Test animations at 4x CPU throttle. Do they stay at 60fps?
Verify will-change elements have cleanup (removed after animation ends).
Key Insight: Do not optimize blindly. Always measure first. The Performance panel recording is your source of truth. If Layout takes 2ms total, adding contain: layout everywhere will not make a meaningful difference. Focus your containment work on the elements that the Performance panel shows are causing the most layout and paint time.

Challenge: Performance-Optimized Card Grid

Build a card grid that uses every containment technique from this module. The grid should handle hundreds of cards efficiently, with smooth hover animations, optimized scroll performance, and proper layer management.

Requirements

  • Grid layout: Use CSS Grid with auto-fill and minmax(280px, 1fr) for responsive columns.
  • Card containment: Each card uses contain: content to isolate layout and paint.
  • Off-screen optimization: Apply content-visibility: auto with contain-intrinsic-size to cards so off-screen cards skip rendering.
  • Hover animation: Animate the card lift effect using transform: translateY(-6px) and a shadow via pseudo-element opacity -- no box-shadow transitions.
  • will-change cleanup: Apply will-change: transform only on :hover so the hint is removed when the cursor leaves.
  • Status indicators: Each card has a colored status dot (green for healthy, yellow for warning, red for error) that pulses using an opacity-only animation (composite safe).
  • Performance proof: If you open DevTools Paint Flashing during hover, only the hovered card should flash green, not the entire grid.

Architecture Hints

  • For the shadow trick: create a .card::after pseudo-element with the final box-shadow value, opacity: 0, and transition opacity on hover. This is cheaper than transitioning box-shadow directly because opacity is composite-only.
  • For the pulsing dot: use @keyframes pulse { 0%, 100% { opacity: 1; } 50% { opacity: 0.4; } } -- this animates only opacity, which is compositor-friendly.
  • Set the grid container itself to contain: layout style so style recalculations from card hovers do not propagate upward.
  • Remember: contain: content is layout + paint + style without size containment, so cards can still size based on their content.
