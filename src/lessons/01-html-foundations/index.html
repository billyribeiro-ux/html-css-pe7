The Building Blocks

Document structure, semantic HTML5 elements, text, lists, links, images, tables, and forms — everything starts here.

1. Document Structure

Every web page you have ever visited is, at its core, a plain text file written in HTML — HyperText Markup Language. Before a browser can render anything on screen, it needs a set of instructions that describe what the content is: a heading, a paragraph, an image, a link. HTML provides those instructions through elements, which are denoted by opening and closing tags.

But HTML is not just a bag of tags you throw at a browser. There is a required structure that every valid HTML document must follow. Think of it like the frame of a house: before you can hang pictures or install plumbing, you need walls, a roof, and a foundation. The document structure is that foundation.

The very first line of any HTML file must be the DOCTYPE declaration. In modern HTML5, this is simply <!DOCTYPE html>. This single line tells the browser: "Render this page using the modern HTML5 standard, not some legacy compatibility mode." Without it, browsers fall back to "quirks mode," which applies inconsistent, outdated rendering rules that can break your layout in subtle and frustrating ways.

After the DOCTYPE, the entire page is wrapped in an <html> element, which is split into two children: <head> and <body>. The head contains metadata — information about the page that is not displayed directly, such as the character encoding, the page title (shown in browser tabs), and links to stylesheets. The body contains every piece of visible content: text, images, forms, everything the user sees and interacts with.

Why this matters: An invalid document structure can cause browsers to guess what you meant. Different browsers guess differently. By writing correct structure from day one, you ensure consistent rendering across Chrome, Firefox, Safari, and Edge. It also improves accessibility — screen readers rely on proper structure to navigate pages.

Anatomy of an HTML Document

HTML 
<!-- The DOCTYPE tells browsers to use HTML5 standards mode -->
<!DOCTYPE html>

<!-- The root element; lang helps screen readers pronounce words correctly -->
<html lang="en">

<head>
  <!-- Character encoding: UTF-8 supports every language and emoji -->
  <meta charset="UTF-8">

  <!-- Viewport meta: essential for responsive design on mobile -->
  <meta name="viewport" content="width=device-width, initial-scale=1.0">

  <!-- Title: appears in browser tab and search engine results -->
  <title>My First Web Page</title>
</head>

<body>
  <!-- All visible content goes here -->
  <h1>Hello, World!</h1>
  <p>This is my first web page.</p>
</body>

</html>

Key Meta Tags Explained

The <meta charset="UTF-8"> tag declares the character encoding for your page. UTF-8 is the universal standard that supports virtually every written language on Earth, plus emoji. If you omit this, special characters like accented letters or symbols might render as garbled text. Always place this tag as the very first element inside <head>.

The <meta name="viewport" ...> tag is critical for mobile devices. Without it, mobile browsers assume your page was designed for a desktop monitor and shrink everything down to fit, making text unreadably small. The width=device-width tells the browser to match the screen width, and initial-scale=1.0 sets the default zoom level to 100%.

The <title> element defines the text shown in the browser tab, in bookmarks, and most importantly in search engine results. It is one of the most impactful SEO elements on any page. A good title is descriptive, concise (under 60 characters), and unique to each page on your site.

2. Semantic Elements

In the early days of the web, developers built entire page layouts using generic <div> elements. A div for the header, a div for the sidebar, a div for the footer — divs everywhere. The problem? A <div> has no inherent meaning. It is just a generic container. When a screen reader encounters a <div>, it has no idea whether it is looking at a navigation menu, a main article, or a footer. This makes the web inaccessible to people using assistive technology.

HTML5 introduced semantic elements — tags that describe the purpose of their content, not just how it looks. Using <header> instead of <div class="header"> tells browsers, screen readers, and search engines exactly what that section of the page represents. Semantics turn your HTML from a soup of meaningless boxes into a well-organized document that machines can understand.

Semantic HTML also improves SEO (Search Engine Optimization). Search engines give higher ranking weight to content inside <main>, <article>, and <h1> elements because they can confidently identify that content as the primary material of the page. Using semantic elements is not just good practice — it is a competitive advantage.

There are also practical benefits for developers. When you return to a project months later, seeing <nav> in your code immediately tells you "this is the navigation." Compare that to <div class="nav-wrapper">, which requires you to read class names and hope they are accurate. Semantic HTML is self-documenting code.

Why this matters: Over 1 billion people worldwide have some form of disability. Semantic HTML is the foundation of web accessibility. It also directly improves your site's search engine rankings, reduces development confusion, and makes your code future-proof. Screen readers use semantic landmarks to let users jump directly to the navigation, main content, or footer.

The Core Semantic Elements

HTML 
<header>     <!-- Site or section header: logo, title, nav -->
<nav>        <!-- Navigation links -->
<main>       <!-- Primary content (only ONE per page) -->
<article>    <!-- Self-contained content (blog post, news story) -->
<section>    <!-- Thematic grouping of content -->
<aside>      <!-- Tangentially related content (sidebar, callout) -->
<footer>     <!-- Site or section footer: copyright, links -->

3. Text Content

Text is the backbone of the web. Even on the most visually stunning website, the actual information is delivered through words. HTML provides a rich set of elements for structuring text content, and choosing the right element is crucial because it affects accessibility, SEO, and the default visual presentation of your content.

Headings (<h1> through <h6>) create a hierarchical outline of your document. Think of them like the headings in a book's table of contents. The <h1> is the title of the page (there should typically be only one per page), <h2> elements are major sections, <h3> elements are subsections within those, and so on. Screen readers allow users to navigate by headings, so a logical heading structure is essential for accessibility. Never skip heading levels — do not jump from <h2> to <h4> without an <h3> in between.

Paragraphs (<p>) are the workhorses of text content. Each <p> represents a distinct block of text. Browsers automatically add vertical spacing between paragraphs, making content easier to scan and read. Never use <br> tags to create spacing between blocks of text — that is what paragraphs are for. The <br> element is only appropriate within a block where a line break is part of the content itself, like a postal address or a poem.

Inline text elements like <strong>, <em>, and <small> add meaning within a sentence. Critically, <strong> means "strong importance" (not just bold), and <em> means "emphasis" (not just italic). A screen reader will change its tone of voice for emphasized text. If you just want visual bold or italic without semantic meaning, use CSS instead. The <small> element represents side comments and small print, such as legal disclaimers or copyright notices.

Why this matters: Proper text markup creates a document outline that screen readers, search engines, and browser extensions can parse. Using <strong> instead of CSS bold tells assistive technology that those words are important. Using headings in order (h1 → h2 → h3) creates a navigable structure for everyone. Search engines also use heading hierarchy to understand the relative importance of content on your page.

Blockquote, Pre, and Code

The <blockquote> element is used for extended quotations from another source. It is a block-level element that browsers typically render with indentation. You can include a <cite> element to attribute the source. For short inline quotations, use <q> instead, which automatically adds quotation marks.

The <pre> element preserves whitespace and line breaks exactly as written in the source code. It is commonly paired with <code> for displaying code blocks. The <code> element on its own is an inline element used to mark up short fragments of computer code within a sentence.

<blockquote>

  <cite>&mdash; Alan Kay</cite>
</blockquote>

  return `Hello, ${name}!`;
}</code></pre>

4. Lists

Lists are one of the most frequently used structures in HTML, and for good reason. Any time you have a collection of related items — navigation links, ingredients, steps in a process, features of a product — a list is the correct semantic choice. Using a list tells browsers and assistive technology that these items are related and belong together as a group.

HTML offers three types of lists. Unordered lists (<ul>) are for items where the sequence does not matter — a grocery list, a set of features, navigation links. Ordered lists (<ol>) are for items where sequence is meaningful — step-by-step instructions, rankings, a table of contents. Description lists (<dl>) are for term-definition pairs — glossaries, metadata, FAQ items.

Screen readers announce lists specially. When a screen reader encounters a <ul> with five items, it will say "list, 5 items" before reading the content. This gives users critical context about how much content to expect. If you fake a list using paragraphs or divs with bullet characters, screen readers cannot provide this context, making your content harder to navigate.

Lists can also be nested inside each other. An <li> within a <ul> can contain another <ul>, creating a hierarchical structure. This is commonly used for multi-level navigation menus, categorized content, and document outlines. The nested list must be placed inside the parent <li>, not after it.

Why this matters: Lists provide semantic grouping that assistive technology relies on. Navigation menus should always be built with lists (usually <ul> inside <nav>). Screen readers announce the number of items, letting users decide whether to explore the list or skip past it. Properly structured lists also help search engines understand grouped content on your page.

5. Links & Navigation

The anchor element (<a>) is arguably the most important element in HTML. It is the element that makes the web a web — connecting pages together into a network of interlinked documents. Without links, every page would be an isolated island. Links are what transformed the internet from a collection of separate files into the interconnected information system we use today.

The href attribute (Hypertext REFerence) specifies where the link points. This can be an absolute URL (https://example.com), a relative path (./about.html), an anchor on the same page (#section-name), an email address (mailto:hello@example.com), or even a phone number (tel:+15551234567). The flexibility of the href attribute makes the anchor element incredibly versatile.

The target attribute controls where the linked page opens. The most common value is _blank, which opens the link in a new tab. However, whenever you use target="_blank", you should also include rel="noopener noreferrer" for security reasons. Without it, the new page could potentially gain access to the originating page's window object, which could be exploited for phishing attacks. Modern browsers handle this automatically in most cases, but including the attribute is still considered best practice.

Good link text is descriptive. Instead of "click here" or "read more," use text that describes the destination: "read our accessibility guide" or "view the pricing page." Screen reader users often navigate by tabbing through links, hearing only the link text — so "click here" repeated five times is useless, while descriptive text is immediately actionable. This is one of the simplest and most impactful accessibility improvements you can make.

Why this matters: Links are the fundamental building blocks of web navigation. Descriptive link text is critical for accessibility — screen reader users often pull up a list of all links on a page, so each link must make sense out of context. Security attributes like rel="noopener" protect your users from cross-site attacks. Using internal anchor links (#id) creates a navigable table of contents within a single page.

6. Images & Media

Images make the web visual and engaging, but they also introduce important considerations around accessibility, performance, and responsive design. The <img> element is a void element (sometimes called a self-closing tag) — it has no closing tag and no child content. Instead, everything about the image is defined through attributes.

The src attribute specifies the path to the image file, and the alt attribute provides alternative text that is displayed when the image cannot load and is read aloud by screen readers. Writing good alt text is an art: it should concisely describe the content and purpose of the image. For decorative images that add no information (like a background pattern or a visual divider), use an empty alt attribute (alt="") so screen readers skip over them entirely rather than announcing "image" with no context.

Performance matters enormously for images. Always include width and height attributes so the browser can reserve the correct amount of space before the image loads, preventing layout shifts that are jarring for users. This metric is called Cumulative Layout Shift (CLS), and it is one of Google's Core Web Vitals that directly affects your search ranking. The loading="lazy" attribute tells the browser to defer loading images that are below the fold (not currently visible), which can dramatically improve initial page load time on image-heavy pages.

The <figure> and <figcaption> elements provide semantic structure for images with captions. A <figure> wraps the image and its caption together, telling the browser and assistive technology that they are related. The <picture> element allows you to provide multiple image sources for different screen sizes or formats, enabling the browser to choose the best one for the user's device and connection speed.

Why this matters: Images without alt text are invisible to screen reader users — they literally do not know the image exists. Missing width/height causes Cumulative Layout Shift (CLS), one of Google's Core Web Vitals that affects search ranking. Lazy loading can cut page load times by 50% or more on image-heavy pages. Using <picture> with modern formats like WebP can reduce file sizes by 30% compared to JPEG.

7. Tables

Tables in HTML are designed for one purpose: displaying tabular data — information that naturally organizes into rows and columns, like spreadsheets, schedules, comparison charts, or financial data. In the early web, tables were infamously abused for page layout, but that practice has been obsolete since the introduction of CSS Flexbox and Grid. Today, tables should only be used for actual data.

A well-structured table uses <thead>, <tbody>, and optionally <tfoot> to separate the header row(s) from the data rows and summary rows. Inside these sections, <tr> (table row) elements contain <th> (table header) cells and <td> (table data) cells. The <th> element is semantically important — it tells screen readers that this cell is a header for the cells in its row or column.

The scope attribute on <th> elements is critical for accessibility. scope="col" means "this header labels the cells below it in this column," while scope="row" means "this header labels the cells to its right in this row." Without scope, screen readers have to guess which cells a header refers to, and they often guess wrong in complex tables.

The <caption> element provides a title or description for the entire table. It must be the first child of the <table> element and is announced by screen readers before they begin reading the table data. Think of it as the table's accessible name — it tells users what data to expect before they dive in. It is also visible on the page, serving as a built-in title for your table.

Why this matters: Screen readers navigate tables cell by cell, and they use <th> and scope to announce which header each data cell belongs to. Without proper markup, a screen reader might say "cell: 42" with no context, instead of "Revenue, Q3: $42,000." Proper table structure makes data comprehensible to everyone. Tables also enable sorting, filtering, and exporting functionality when combined with JavaScript.

8. Forms

Forms are the primary way users send data to a website. Every login screen, search bar, checkout page, and registration form is built with HTML form elements. Understanding forms deeply is essential because they are the most interactive and complex part of HTML, and getting them right means the difference between a frustrating user experience and a smooth one.

The <form> element is the container that wraps all form controls. It has two critical attributes: action (the URL where form data is sent) and method (usually GET for searches or POST for data submission). When a user clicks a submit button inside a form, the browser collects all the form data and sends it to the server specified in the action. Each form control must have a name attribute, which becomes the key in the submitted data.

Every form control must have an associated <label> element. Labels serve two purposes: they tell users (and screen readers) what information a field expects, and they make the field clickable by its label text (a bigger click target). You connect a label to its input using the for attribute on the label, matching the id on the input. Alternatively, you can wrap the input inside the label element. Never, ever create a form field without a label — it is the single most common accessibility violation on the web.

HTML5 introduced a wealth of input types beyond the basic text field: email, number, date, range, color, tel, url, and more. These types do two things: they trigger specialized keyboard layouts on mobile devices (the email type shows the @ key, the number type shows a numeric keypad), and they provide built-in browser validation (the email type rejects values without an @). Using the correct input type gives your users a better experience at zero cost to you. The <fieldset> and <legend> elements group related controls together, which is especially important for radio buttons and checkboxes that share a common question or label.

Why this matters: Forms without labels are the number one accessibility violation on the web. Proper labels, fieldsets, and input types make forms usable for everyone — sighted users, screen reader users, keyboard-only users, and mobile users. Built-in validation through input types reduces JavaScript you need to write and gives users immediate feedback. The required attribute prevents form submission without needed data, and minlength/maxlength enforce text length limits natively.

Exercise: Build a Personal Profile Page

Using everything you have learned in this module, build a complete personal profile page from scratch. Your page must use proper document structure and semantic elements throughout.

  1. Start with a valid HTML5 document structure: DOCTYPE, html (with lang), head (with charset, viewport, title), and body.
  2. Use a <header> with your name as an <h1> and a <nav> with at least three links (Home, About, Contact) that use anchor links to sections on the page.
  3. Use <main> to wrap your primary content.
  4. Create an "About Me" <section> with at least two paragraphs describing yourself. Use <strong> and <em> where appropriate.
  5. Add a "Skills" <section> with an unordered list of your skills. Include at least one nested list (e.g., "Programming" with sub-items "HTML," "CSS," "JavaScript").
  6. Add an "Experience" <section> with a description list (<dl>) of your job history or education (term = role/school, definition = description).
  7. Include a profile image using <figure> and <figcaption>. Use a placeholder image service like https://placehold.co/300x300 and write descriptive alt text.
  8. Add a "Contact Me" <section> with a form that includes: name (text), email (email), subject (select dropdown), message (textarea), and a submit button. Every field must have a proper <label>.
  9. Use a <footer> with a copyright notice and at least one external link (e.g., to your GitHub or LinkedIn) with proper target and rel attributes.
  10. Validate your page using the W3C HTML Validator and fix any errors.

Challenge: Build a Recipe Page

Create a full recipe page that combines every concept from this module. This challenge tests your ability to choose the right semantic elements for each type of content.

  • Title and Description: Use a <header> with the recipe name as <h1>, a <figure> with a food photo (use a placeholder), and two paragraphs describing the dish and its origin.
  • Ingredients: An unordered list (<ul>) of all ingredients, grouped by category using nested lists (e.g., "For the sauce:" as a parent item with sub-items for each sauce ingredient).
  • Steps: An ordered list (<ol>) of cooking instructions. Each step should be a detailed paragraph, not just a sentence.
  • Nutrition Table: A properly structured <table> with <caption>, <thead>, <tbody>, and <th scope> attributes showing nutritional information (Calories, Protein, Carbs, Fat per serving).
  • Review Form: A form where users can submit a review: name (text), email (email), rating (range slider 1–5 with <output> display), would-recommend (radio buttons: Yes/No), and review text (textarea). Group related fields with <fieldset> and <legend>.
  • Semantic Structure: Use <article> for the recipe, <section> for each part (ingredients, steps, nutrition, reviews), <aside> for a "Chef's Tips" sidebar, and a proper <footer>.
