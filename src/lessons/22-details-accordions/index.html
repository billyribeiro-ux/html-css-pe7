Exclusive Accordions & Details Styling

Master the native <details> disclosure widget: build exclusive accordion groups with zero JavaScript, animate open/close with ::details-content, and create production-ready FAQ panels, settings interfaces, and nested navigation systems using only HTML and CSS.

1. <details> and <summary> Basics

The <details> element is HTML's native disclosure widget. It creates a collapsible section that the user can toggle open or closed. The <summary> child element provides the visible heading that acts as the toggle control. Everything else inside <details> is the content that gets shown or hidden.

This is not a hack or a clever CSS trick. The <details> element is part of the HTML specification, carries built-in keyboard and screen reader support, and requires zero JavaScript to function. It is the correct semantic element for expandable content sections.

Basic Structure

HTML

<details>
  <summary>What is the return policy?</summary>
  <p>You can return any item within 30 days
     of purchase for a full refund.</p>
</details>

<!-- Open by default -->
<details open>
  <summary>Shipping Information</summary>
  <p>Free shipping on orders over $50.
     Standard delivery takes 3-5 business days.</p>
</details>

Key Behaviors

  • Toggle on click: Clicking <summary> toggles the open attribute on <details>.
  • Keyboard accessible: Enter and Space toggle the element when <summary> has focus.
  • Default marker: Browsers render a disclosure triangle (▸) via the ::marker pseudo-element on <summary>.
  • The open attribute: A boolean HTML attribute. When present, the content is visible. You can set it in HTML or toggle it via JavaScript.
  • Semantic meaning: Screen readers announce <summary> as a button with an expanded/collapsed state.

What is the <details> element?

The <details> element is a native HTML disclosure widget that creates expandable/collapsible content sections. It requires no JavaScript and is fully accessible out of the box.

This one starts open

Because the open attribute is present in the HTML, this section is visible by default. The user can click to close it, or it can be programmatically controlled.

Can it contain any content?

Yes. The content area can contain paragraphs, lists, images, code blocks, other <details> elements (nesting), tables, forms -- anything that makes sense semantically.

  • Paragraphs and text
  • Images and media
  • Nested details elements
  • Code blocks and tables
Key Insight: The <details> element fires a toggle event when it opens or closes. You can listen for this in JavaScript, but you never need JavaScript just to make the toggle work. The browser handles it natively.

Why Native <details> Over JS Accordions

A JavaScript accordion component can do everything <details> can do and more. So why reach for the native element? Because of what you get without writing or shipping anything: keyboard interaction (Enter, Space, Tab), screen reader announcements (expanded/collapsed state), and browser find-in-page that searches inside collapsed content. A JS accordion must reimplement all of this, and most implementations get at least one of those wrong.

The trade-off is real, though. Native <details> has historically had no animation support at all -- content snapped open and closed instantly. The ::details-content pseudo-element and interpolate-size: allow-keywords fix this, but they are recent additions (widespread browser support arrived in 2024-2025). If your project requires smooth animation in older browsers, you face a genuine decision. A PE7 weighs these factors honestly: native semantics and free accessibility on one side, animation fidelity on the other. In most cases the native element wins, because the animation is a progressive enhancement -- the accordion still works perfectly without it. But if your design system mandates animated transitions as a hard requirement across all supported browsers, a custom component with proper ARIA attributes may be the right call. The key is making that choice deliberately, not defaulting to a JS library out of habit.

2. Exclusive Accordions

Traditionally, building an accordion where only one panel is open at a time required JavaScript event listeners to close all other panels when one opens. The name attribute on <details> eliminates this entirely.

When multiple <details> elements share the same name attribute value, they form an exclusive accordion group. Opening one automatically closes the others. The browser handles the mutual exclusion natively -- no scripts, no state management, no event delegation.

Syntax

HTML

<!-- These three form an exclusive group -->
<details name="faq">
  <summary>Question 1</summary>
  <p>Answer 1...</p>
</details>

<details name="faq">
  <summary>Question 2</summary>
  <p>Answer 2...</p>
</details>

<details name="faq">
  <summary>Question 3</summary>
  <p>Answer 3...</p>
</details>

<!-- This one is in a DIFFERENT group -->
<details name="settings">
  <summary>Account Settings</summary>
  <p>Does not affect the "faq" group.</p>
</details>

Multiple Groups on One Page

You can have as many accordion groups as you need. Each group is identified by its name value. Groups are completely independent of each other: opening an item in one group does not affect items in another group.

HTML

<!-- Group 1: FAQ -->
<details name="faq">...</details>
<details name="faq">...</details>

<!-- Group 2: Settings -->
<details name="settings">...</details>
<details name="settings">...</details>

<!-- Standalone (no name = independent toggle) -->
<details>...</details>

How does the exclusive accordion work?

When multiple <details> elements share the same name attribute, the browser automatically closes the currently open one when you open another. This is called an "exclusive accordion" or "mutually exclusive disclosure group."

Do I need JavaScript for this?

No. The name attribute is a native HTML feature. The browser handles the mutual exclusion logic entirely on its own. This has been supported in all major browsers since 2024.

Can I have multiple groups on the same page?

Absolutely. Each group is identified by its unique name value. You can have name="faq", name="settings", and name="specs" all on the same page, and they will operate independently.

What happens if I omit the name attribute?

Without a name attribute, each <details> element operates independently. Multiple items can be open simultaneously, which is sometimes the desired behavior (e.g., a documentation page where users want to compare multiple sections).

Exclusive Accordions and the UX Trade-Off

The name attribute is deceptively simple: add the same string to a group of <details> elements and the browser enforces mutual exclusion. No event listeners, no state management, no "close all siblings" loop. This is the kind of feature that eliminates an entire category of bugs -- the accordion that sometimes leaves two panels open, the race condition when users click quickly, the forgotten cleanup when panels are added dynamically.

But before you add name to every accordion, consider the user's mental model. Exclusive accordions work well for FAQ pages, where users typically want one answer at a time, and for settings panels, where screen real estate is limited. They are the wrong choice when users need to compare content across panels -- API documentation where someone is cross-referencing two endpoints, or a product comparison where multiple spec sections should stay open. Omitting the name attribute gives you independent toggles, which is sometimes exactly what the user needs. A PE7 does not default to exclusive behavior because it is clever; they choose it when the interaction model calls for it, and they leave it off when users benefit from having multiple panels open simultaneously.

3. The ::details-content Pseudo-Element

The ::details-content pseudo-element targets the content wrapper inside a <details> element -- everything except the <summary>. This pseudo-element is the key to animating the open/close transition, because it gives you a CSS handle on the collapsible region itself.

What It Targets

HTML

<details>
  <summary>Click me</summary>
  <!-- Everything below is ::details-content -->
  <p>This paragraph...</p>
  <p>...and this paragraph...</p>
  <ul><li>...and this list</li></ul>
  <!-- All wrapped by ::details-content -->
</details>

CSS

/* Target the content area */
details::details-content {
  /* This is the wrapper around everything
     except <summary> */
  padding: 1rem;
  background: #1a1d27;
  border-top: 1px solid #2e3345;
}

/* Style differently when open */
details[open]::details-content {
  /* Styles applied only when expanded */
  opacity: 1;
}

Why It Matters for Animation

Before ::details-content, there was no clean way to target the collapsible region. You had to wrap your content in an extra <div> and style that instead, but you still could not animate the actual show/hide because the browser controlled it. With ::details-content, you can directly apply height, opacity, and overflow transitions to the content wrapper, giving you full control over the open/close animation.

Key Insight: The ::details-content pseudo-element has display: block when the <details> is open and the browser's default hidden state when closed. This is what makes height transitions possible -- you are transitioning an element between display: none (closed) and display: block (open), which now works with transition-behavior: allow-discrete.

4. Animating Open/Close

This is where the real magic happens. Combining ::details-content with modern CSS transition features gives you smooth, animated accordion open/close without a single line of JavaScript. The recipe involves four ingredients working together.

The Four Ingredients

1

::details-content

Targets the collapsible content wrapper. Set its closed state to height: 0 with overflow: hidden, and its open state to height: auto.

2

interpolate-size

The property interpolate-size: allow-keywords on :root tells the browser it is allowed to transition to and from keyword sizes like auto. Without this, height: 0 to height: auto cannot animate.

3

@starting-style

Defines the initial style that applies at the moment an element first appears (entry animation). This lets you animate the content appearing from height: 0 when the details opens.

4

transition-behavior

The value allow-discrete permits transitions on discrete properties like display and content-visibility. This prevents the content from vanishing instantly on close.

The Complete Recipe

CSS

/* Step 1: Enable keyword interpolation globally */
:root {
  interpolate-size: allow-keywords;
}

/* Step 2: Style the closed state */
details::details-content {
  height: 0;
  overflow: hidden;
  opacity: 0;
  transition:
    height 0.4s ease,
    opacity 0.4s ease,
    content-visibility 0.4s ease allow-discrete;
}

/* Step 3: Style the open state */
details[open]::details-content {
  height: auto;
  opacity: 1;
}

/* Step 4: Define the entry animation start point */
@starting-style {
  details[open]::details-content {
    height: 0;
    opacity: 0;
  }
}

How It Works Step by Step

  1. Closed state: ::details-content has height: 0 and overflow: hidden, so the content is invisible and takes no space.
  2. User clicks summary: The browser adds the open attribute. The [open]::details-content rule applies, setting height: auto.
  3. Entry transition: Because @starting-style says "start from height: 0", the browser transitions from 0 to auto (possible because of interpolate-size: allow-keywords).
  4. User clicks again: The open attribute is removed. The element transitions back from height: auto to height: 0.
  5. Discrete cleanup: content-visibility with allow-discrete ensures the content remains visible during the closing transition instead of disappearing instantly.

Demo: Animated Exclusive Accordion

Click any item below. The content smoothly animates open while the previously open item animates closed. This uses the full recipe: ::details-content + interpolate-size + @starting-style.

What makes this animation smooth?

The combination of interpolate-size: allow-keywords (enabling height: 0 to height: auto transitions), ::details-content (targeting the collapsible wrapper), and @starting-style (defining the entry state) creates a smooth CSS-only open/close animation.

There is zero JavaScript involved. The browser handles everything: the mutual exclusion logic, the transition timing, and the discrete property changes.

Is interpolate-size safe to use globally?

Yes. Setting interpolate-size: allow-keywords on :root is safe. It simply enables the browser to interpolate between keyword values (like auto) and explicit values (like 0) during transitions. It does not change any existing behavior -- it only unlocks new capabilities.

What about browser support?

As of 2026, ::details-content, interpolate-size, and @starting-style are supported in Chrome, Edge, Safari, and Firefox. The <details name="..."> exclusive accordion feature has been in all browsers since late 2024.

For older browsers, the accordion still works perfectly -- it just opens and closes instantly without animation. This is ideal progressive enhancement.

Can I customize the easing and duration?

Absolutely. The transition properties on ::details-content accept all standard timing functions: ease, ease-in-out, cubic-bezier(), linear(), and spring(). Duration and delay work exactly as you would expect from any CSS transition.

Key Insight: The @starting-style block is essential for the opening animation. Without it, the browser has no "from" state when the element first appears, so the transition would not play on open -- only on close. Think of @starting-style as defining the "from" keyframe of an entry transition.

5. Styling Patterns

With the fundamentals in place, let us build real-world components. These patterns cover the most common accordion use cases you will encounter in production: FAQ layouts, settings panels, specification tables, and custom markers.

Custom Markers & Icon Rotation

The default disclosure triangle comes from the ::marker pseudo-element on <summary>. You can remove it and replace it with a custom icon that rotates on open.

CSS

/* Remove the default marker */
summary {
  list-style: none;
}
summary::-webkit-details-marker {
  display: none;
}

/* Add a custom chevron */
summary::after {
  content: "\276F"; /* right chevron */
  transition: rotate 0.3s ease;
}

/* Rotate when open */
details[open] > summary::after {
  rotate: 90deg;
}

6. Advanced Patterns

With a solid foundation in details/summary, exclusive groups, and animation, we can build more sophisticated interfaces. These patterns use :has(), creative selectors, and structural composition to solve real design problems.

Styling Parents with :has(details[open])

The :has() selector lets you style a container based on whether any of its <details> children are open. This enables effects like changing the container background, adding a glow, or adjusting layout when content is expanded.

CSS

/* Highlight the container when any accordion is open */
.accordion-wrapper:has(details[open]) {
  border-color: #6c5ce7;
  box-shadow: 0 0 20px rgba(108, 92, 231, 0.15);
}

/* Show a "collapse all" hint when something is open */
.accordion-wrapper:has(details[open])::after {
  content: "Click another item to switch";
  display: block;
  text-align: center;
  font-size: 0.75rem;
  color: #8b8fa7;
  padding-top: 0.75rem;
}

/* Count open items (with non-exclusive accordions) */
.multi-accordion:has(details[open] ~ details[open]) {
  /* Two or more are open */
  border-left: 3px solid #fdcb6e;
}

When <details> Is the Right Tool -- and When It Is Not

<details> is the right element when the interaction is genuinely "show me more about this item." FAQ pages, settings panels, specification tables, mobile navigation menus, collapsible sidebar sections, release notes -- these are all natural fits. The content is secondary or supplementary, the user chooses what to reveal, and the page makes sense even with everything collapsed.

It is the wrong element when the content sections are peers that the user must choose between as part of a workflow. Tabbed interfaces are the classic example: tabs imply that exactly one panel is always visible and the content areas are parallel alternatives, not progressive disclosure. A stepper or wizard implies sequential progression. A carousel implies browsing. These patterns share surface-level similarity with accordions (you see one thing at a time), but they carry different semantics and user expectations. Wrapping tabs in <details> elements would confuse screen readers, break expected keyboard patterns (tabs use arrow keys, not Enter/Space), and misrepresent the relationship between panels. A PE7 does not use <details> just because it avoids JavaScript -- they match the HTML element to the actual interaction model.

7. Accessibility

The <details> and <summary> elements come with built-in accessibility features. However, there are best practices to follow and pitfalls to avoid to ensure your accordions work well for all users.

Built-In Behaviors

  • Keyboard navigation: <summary> is focusable by default. Enter and Space toggle the open state. Tab moves focus to the next focusable element.
  • Screen reader announcements: <summary> is announced as a disclosure widget with its current state (expanded or collapsed). Most readers say something like "disclosure triangle, collapsed" or "button, expanded."
  • Implicit role: <summary> has an implicit ARIA role of button (when it is the first child of <details>). You do not need to add role="button".
  • State communication: The expanded/collapsed state is communicated automatically. You do not need aria-expanded on summary elements -- the browser handles this.

Best Practices

HTML

<!-- GOOD: summary is the first child -->
<details>
  <summary>Descriptive label here</summary>
  <p>Content...</p>
</details>

<!-- GOOD: Accordion group with headings -->
<h2>Frequently Asked Questions</h2>
<details name="faq">
  <summary>Clear, concise question text</summary>
  <p>Detailed answer...</p>
</details>

<!-- AVOID: Non-descriptive summary -->
<details>
  <summary>Click here</summary>
  <p>Not helpful for screen reader users.</p>
</details>

<!-- AVOID: Adding role="button" (already implicit) -->
<details>
  <summary role="button">Redundant</summary>
</details>

<!-- AVOID: Interactive elements inside summary -->
<details>
  <summary>
    Topic
    <button>Edit</button> <!-- Bad: nested interactive -->
  </summary>
</details>

Animation Accessibility

Always respect the user's motion preferences. If they have prefers-reduced-motion enabled, remove or minimize accordion animations.

CSS

/* Respect motion preferences */
@media (prefers-reduced-motion: reduce) {
  details::details-content {
    transition-duration: 0.01s;
  }
}

/* Or remove transitions entirely */
@media (prefers-reduced-motion: reduce) {
  details::details-content {
    transition: none;
  }
}

ARIA Considerations

Do

  • Use descriptive text in <summary>
  • Keep <summary> as the first child
  • Provide visible focus styles on summary
  • Respect prefers-reduced-motion
  • Use heading elements before accordion groups for context
  • Test with a screen reader (VoiceOver, NVDA, JAWS)

Don't

  • Put interactive elements (buttons, links) inside <summary>
  • Add role="button" or aria-expanded to <summary>
  • Use <details> for content that should always be visible
  • Hide critical information (like error messages) in closed accordions
  • Rely solely on color changes to indicate the open/closed state
  • Remove the focus outline without providing an alternative
Key Insight: The browser's built-in accessibility for <details>/<summary> is already excellent. The most common mistake is adding ARIA attributes that conflict with the native semantics. Trust the platform: use the elements correctly and the accessibility comes for free.

Progressive Enhancement as an Architectural Principle

<details> works with zero CSS and zero JavaScript. If your stylesheet fails to load, the accordion still functions -- users can still expand and collapse sections, read all the content, and navigate with the keyboard. If JavaScript is blocked or broken, nothing changes. This is not an accident; it is the defining property of a well-chosen HTML element.

Compare this to a JS accordion built with <div> elements and click handlers. If the script fails, the user sees either all panels at once (confusing) or no panels at all (broken). The JS accordion requires explicit work to degrade gracefully; the <details> element degrades gracefully by default. This is a PE7 architectural principle that extends beyond accordions: choose HTML elements that carry behavior, not just semantics. <details> for disclosure, <dialog> for modals, <input type="date"> for date pickers. Every native element you use is one fewer component that can break in production. CSS and JavaScript enhance the experience -- custom animations, styled markers, exclusive groups -- but the baseline functionality should never depend on them.

  • Responsive layout: Side-by-side panels on desktop, stacked on mobile.
  • Accessibility: Proper focus styles and prefers-reduced-motion support.

Architecture Hints

  • Use CSS Grid with grid-template-columns: 1fr 1fr for the two-panel layout, switching to 1fr on narrow screens.
  • For plus/minus markers: use summary::after { content: "+"; } and details[open] > summary::after { content: "\2212"; } (the minus sign).
  • For the :has() glow effect: .panel:has(details[open]) { box-shadow: 0 0 20px rgba(108, 92, 231, 0.15); }
  • Use different name values for each group: name="actions", name="status", and name="nested-sub" for the nested level.
  • Wrap each panel in a container div for the :has() targeting to work correctly.
