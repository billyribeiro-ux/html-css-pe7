Color Science for the Web

Master modern CSS color spaces, perceptually uniform palettes with OKLCH, dynamic color mixing, relative color syntax, and accessible theming with light-dark() — building complete color systems from first principles.

1. Beyond sRGB

For decades, web colors were confined to the sRGB color space — a standard defined in 1996 that covers only about 35% of visible colors. Modern displays (especially OLED and Apple's P3 screens) can render far more vivid, saturated colors than sRGB allows. CSS now gives us the tools to use them.

Why New Color Spaces Matter

Human color perception is non-linear. A change of 10 units in one part of HSL looks dramatically different from the same change in another part. Colors that appear "equally bright" in HSL often look wildly different to the human eye. New color spaces like OKLCH were designed to match how we actually perceive color.

Perceptual Uniformity: In a perceptually uniform color space, equal numerical changes produce equal perceived changes. If you increase lightness by 10% in OKLCH, the result looks 10% lighter regardless of hue. In HSL, the same change might look barely different for yellows but dramatic for blues. This is why OKLCH is revolutionizing CSS color systems.

2. OKLCH

OKLCH stands for OK Lightness Chroma Hue — a perceptually uniform, cylindrical color space that is quickly becoming the recommended way to define colors in modern CSS.

Syntax

/* oklch(lightness chroma hue) */
color: oklch(0.7 0.15 145);    /* a vivid green */
color: oklch(0.5 0.2 25);      /* a saturated red */
color: oklch(0.9 0.05 90);     /* a soft yellow */
color: oklch(0.3 0.0 0);       /* dark gray (zero chroma = neutral) */

/* With alpha */
color: oklch(0.7 0.15 145 / 0.5);  /* 50% transparent */

The Three Channels

  • Lightness (L): 0 (black) to 1 (white). Perceptually uniform — 0.5 truly looks "half bright."
  • Chroma (C): 0 (gray) to ~0.4 (maximum saturation). Controls vividness without affecting perceived brightness.
  • Hue (H): 0–360 degrees around the color wheel. Similar to HSL hue but perceptually spaced.

Why OKLCH Over HSL/RGB for Design Systems

The real argument for OKLCH is not "perceptually uniform" as an academic property -- it is that OKLCH makes your color system composable. When you build a design system, you need to programmatically generate color scales: take a brand blue and produce 10 tints, 5 shades, hover states, disabled states, dark-mode variants. In HSL, this breaks down immediately. HSL's "50% lightness" produces a yellow that looks blazing bright and a blue that looks nearly dark -- your generated scales will look inconsistent, and designers will override them with hand-picked values, defeating the purpose of a system.

With OKLCH, L = 0.6 looks like the same perceived brightness whether the hue is blue, yellow, or red. This means a single formula like "lighten by 0.15 for hover" works across every color in your palette without per-hue exceptions. At PE7 level, you pick color spaces that reduce the number of manual overrides in your system. Fewer overrides means fewer maintenance points, fewer bugs when brand colors change, and faster onboarding for new engineers who can trust the formulas instead of memorizing magic values.

3. color-mix()

The color-mix() function blends two colors together in a specified color space. It eliminates the need for manually calculating intermediate colors and is the foundation for generating tints, shades, and tones programmatically in CSS.

Syntax

/* color-mix(in colorspace, color1 percentage, color2) */
color: color-mix(in oklch, blue 70%, white);       /* 70% blue + 30% white */
color: color-mix(in oklch, #e74c3c 50%, #3498db);  /* equal mix of red & blue */
color: color-mix(in srgb, black 20%, currentColor); /* darken any color by 20% */

/* Generate tints (mix with white) */
--tint-10: color-mix(in oklch, var(--brand) 90%, white);
--tint-30: color-mix(in oklch, var(--brand) 70%, white);
--tint-50: color-mix(in oklch, var(--brand) 50%, white);

/* Generate shades (mix with black) */
--shade-10: color-mix(in oklch, var(--brand) 90%, black);
--shade-30: color-mix(in oklch, var(--brand) 70%, black);
--shade-50: color-mix(in oklch, var(--brand) 50%, black);

color-mix() vs Custom Properties: When to Use Which

You might wonder: why not just pre-compute every color as a custom property and skip color-mix() entirely? The trade-off comes down to flexibility versus inspectability. Pre-computed tokens like --blue-300: oklch(0.78 0.12 250) are fully visible in DevTools -- you can see the exact resolved value, copy it, and reason about it. This matters when debugging visual issues at 2 AM.

color-mix() shines when the inputs are dynamic. If your brand color is a custom property that can change (theming, white-labeling, user preferences), then color-mix(in oklch, var(--brand) 30%, white) automatically recomputes every derived shade when --brand changes. Pre-computed tokens cannot do this -- you would need JavaScript to recalculate every value in the scale. However, color-mix() results currently show as opaque computed values in most DevTools, making debugging harder.

The PE7 approach: use pre-computed OKLCH tokens for your base palette (the values that do not change per-theme), and use color-mix() for values that must react to runtime changes -- theme switching, user-configurable brand colors, or contextual adjustments like "20% lighter than whatever the parent's background is." Do not default to one approach for everything.

4. Relative Color Syntax

Relative color syntax lets you derive a new color from an existing one by adjusting individual channels. This is incredibly powerful for building entire palettes from a single base color, creating hover states, or manipulating opacity — all without JavaScript.

Syntax

/* oklch(from base-color lightness chroma hue) */
--brand: oklch(0.6 0.2 250);

/* Lighten by 20% */
--brand-light: oklch(from var(--brand) calc(l * 1.2) c h);

/* Desaturate */
--brand-muted: oklch(from var(--brand) l calc(c * 0.5) h);

/* Shift hue for complementary */
--brand-complement: oklch(from var(--brand) l c calc(h + 180));

/* Darken and increase saturation */
--brand-dark: oklch(from var(--brand) calc(l * 0.7) calc(c * 1.3) h);

/* Add transparency */
--brand-faded: oklch(from var(--brand) l c h / 0.3);

5. light-dark()

The light-dark() function selects one of two color values based on the user's current color scheme preference. It requires color-scheme: light dark to be set, and then automatically resolves to the appropriate value.

Syntax

/* Required: declare supported color schemes */
:root {
  color-scheme: light dark;
}

/* light-dark(light-value, dark-value) */
body {
  color: light-dark(#333, #eee);
  background: light-dark(#fff, #1a1a2e);
}

.card {
  background: light-dark(#f8f9fa, #2d2d44);
  border-color: light-dark(#dee2e6, #404060);
  box-shadow: light-dark(
    0 2px 8px rgba(0, 0, 0, 0.1),
    0 2px 8px rgba(0, 0, 0, 0.4)
  );
}

6. Building a Color System

With OKLCH and color-mix(), you can build a complete, systematic color palette from just a few base values. The approach: define base colors in OKLCH, then generate tint scales (10–90), semantic tokens, and surface colors — all derived mathematically.

Complete Palette Architecture

:root {
  /* Base colors in OKLCH */
  --primary:   oklch(0.55 0.2 250);
  --secondary: oklch(0.6 0.15 160);
  --accent:    oklch(0.65 0.22 30);

  /* Tint scale: mix base with white */
  --primary-10: color-mix(in oklch, var(--primary) 10%, white);
  --primary-20: color-mix(in oklch, var(--primary) 20%, white);
  --primary-30: color-mix(in oklch, var(--primary) 30%, white);
  --primary-40: color-mix(in oklch, var(--primary) 40%, white);
  --primary-50: color-mix(in oklch, var(--primary) 50%, white);
  --primary-60: color-mix(in oklch, var(--primary) 60%, white);
  --primary-70: color-mix(in oklch, var(--primary) 70%, white);
  --primary-80: color-mix(in oklch, var(--primary) 80%, white);
  --primary-90: color-mix(in oklch, var(--primary) 90%, white);

  /* Semantic colors */
  --success: oklch(0.6 0.18 145);
  --warning: oklch(0.75 0.18 80);
  --error:   oklch(0.55 0.22 25);
  --info:    oklch(0.6 0.15 240);
}

7. Wide-Gamut Colors

Display P3 covers about 50% more colors than sRGB. With the color() function and the @media (color-gamut: p3) query, you can serve more vivid colors to capable displays while providing sRGB fallbacks for standard screens.

Using P3 Colors with Fallbacks

/* sRGB fallback first, then P3 override */
.vibrant-button {
  background: #e74c3c;  /* sRGB fallback */
  background: color(display-p3 0.96 0.2 0.15);  /* P3 override */
}

/* Or use @supports for targeted enhancement */
@supports (color: color(display-p3 1 0 0)) {
  .vibrant-cta {
    background: color(display-p3 1 0.15 0.3);
  }
}

/* Media query for gamut detection */
@media (color-gamut: p3) {
  :root {
    --accent: oklch(0.7 0.3 30);  /* higher chroma available */
  }
}

@media (color-gamut: srgb) {
  :root {
    --accent: oklch(0.7 0.18 30);  /* clamp chroma for sRGB */
  }
}

Gamut and Production Reality: Design in sRGB First

Wide-gamut colors are seductive in demos -- those hyper-vivid P3 reds and greens look incredible on a MacBook Pro. But in production, your users are on a mix of sRGB office monitors, budget Android phones, projectors in conference rooms, and older laptops. When a P3 color lands on an sRGB display, the browser clips it to the nearest sRGB value. That clipping is not perceptually uniform -- it can shift hues, crush details in gradients, and make carefully tuned color relationships fall apart.

The PE7 rule: design your entire system in sRGB first, ensure it works and meets contrast requirements on standard displays, and then layer in wide-gamut enhancements using @media (color-gamut: p3) or @supports. This is the same progressive enhancement mindset you apply everywhere else. The color() function with explicit gamut mapping (color(display-p3 ...)) gives browsers instructions for how to handle out-of-gamut situations, but you should never rely on a P3-only color for conveying meaning or meeting accessibility thresholds. If your error state only looks red enough on P3 displays, you have a production bug on every sRGB screen.

8. Accessibility

Modern color features must work hand-in-hand with accessibility. CSS provides forced-colors mode for users who need high-contrast system colors, and prefers-contrast for those who want more or less contrast than default.

Forced Colors & Contrast Preferences

/* Respect forced-colors mode (Windows High Contrast, etc.) */
@media (forced-colors: active) {
  .card {
    border: 2px solid CanvasText;
    background: Canvas;
    color: CanvasText;
  }

  .button {
    border: 2px solid ButtonText;
    background: ButtonFace;
    color: ButtonText;
    forced-color-adjust: none;  /* opt out selectively */
  }
}

/* Respond to contrast preferences */
@media (prefers-contrast: more) {
  :root {
    --text: oklch(0.1 0 0);
    --bg: oklch(1 0 0);
    --border-width: 2px;
  }
}

@media (prefers-contrast: less) {
  :root {
    --text: oklch(0.35 0 0);
    --bg: oklch(0.95 0 0);
  }
}

/* Combine with color scheme awareness */
@media (prefers-contrast: more) and (prefers-color-scheme: dark) {
  :root {
    --text: oklch(0.95 0 0);
    --bg: oklch(0.05 0 0);
  }
}

forced-colors and the Colors You Cannot Control

Windows High Contrast mode (and its modern successor, forced-colors) is not a niche concern -- it is used by millions of people with low vision, migraines, light sensitivity, and cognitive disabilities. When forced-colors: active is in effect, the browser overrides nearly all of your color declarations with system colors. Your carefully crafted oklch palette, your color-mix scales, your light-dark toggles -- all of it gets replaced. This is by design, and fighting it is the wrong approach.

What a PE7 engineer does instead: ensure your UI is understandable through structure, not color alone. Borders, outlines, and text remain visible in forced-colors mode, but backgrounds, shadows, and gradients do not. If you rely on a colored background to indicate an error state, that signal disappears. Use @media (forced-colors: active) to add visible borders, ensure icons have forced-color-adjust: auto so they pick up system colors, and test with the "Emulate CSS media feature forced-colors" toggle in Chrome DevTools. The key insight: forced-color-adjust: none lets you opt specific elements out of forced-colors overrides, but use it sparingly and only when you can guarantee contrast yourself -- data visualizations and color swatches are valid cases, decorative gradients are not.

Challenge: Complete Accessible Color System

Build a fully accessible color system using light-dark() derived from 3 OKLCH base values. The system should automatically adapt to light and dark mode, respond to contrast preferences, and maintain WCAG AA contrast ratios throughout.

Requirements

  • Define 3 OKLCH base colors: primary, secondary, and accent.
  • Generate a full tint/shade scale (10–90) for each base using color-mix().
  • Use light-dark() for all color assignments so the entire UI adapts automatically.
  • Add @media (prefers-contrast: more) overrides that increase contrast ratios.
  • Add @media (forced-colors: active) support using system color keywords.
  • Build at least three components (card, button, alert) that demonstrate the full system.
  • All text must meet WCAG AA contrast ratio (4.5:1 for normal text, 3:1 for large text).
  • Include a visual contrast checker showing foreground/background pairings and their approximate ratios.

Hints

  • Set color-scheme: light dark on :root first — light-dark() will not work without it.
  • In OKLCH, a lightness difference of at least 0.4 between text and background typically satisfies WCAG AA.
  • Use color-mix() with transparent as the second color to create alpha variants.
  • For forced-colors mode, use system keywords: Canvas, CanvasText, LinkText, ButtonFace, ButtonText.
